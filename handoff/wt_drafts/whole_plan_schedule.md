## 4. 일정을 움직이는 요인

### 4.1 가장 큰 세 가지

1. **card당 검증·조율 비용과 직렬 gate**: Phase 2 후반 1.7 h/card에서 Phase 3 창 4~6.7 h/card로 늘었다(2.2). 바뀐 줄의 68%가 판정 기록, 22%가 문서이고 code는 1.7%다. card당 agent는 약 40회, 승인 기록은 약 1건이다(2.4). gate가 한 번에 한 변경이라 병렬 agent가 이 비용을 나누지 못한다. 민감도: card당 1 h가 늘거나 줄 때마다 208장 × 1 h ≈ 208 h ≈ **달력 약 35일**이 바뀐다(추정 = 208 / 10.5 / 0.57).
2. **미설계 Phase의 card 수와 끼어드는 card**: 5~7c는 90~180장 범위다(r 1.0~2.0). 준비 중에 card가 계속 생긴다. Phase 3에서는 T0·FU·B33·G1·V4 강화가 이렇게 생겼고, 백로그는 활동일당 약 4건씩 늘고 있다(B56~B68). r이 0.5 바뀌면 45장 ≈ 180 h(중앙 h) ≈ **달력 약 30일**이 바뀐다.
3. **사용자 결정·승인 대기와 활동일 비율**: 활동일 비율은 0.53~0.57이다(10-02 → 10-06 3.7일 공백). 이 세션에서 AskUserQuestion이 22회였고, design 승인(DEC-51)이 7회 더 남았다. 6a-2 J ratify, Phase 4 UD-0·UD-1·UD-6·UD-15·UD-17a~e, 동작 변경마다 DEC-40 기준선 승인도 남아 있다. 활동일 비율이 0.57에서 0.8로 오르면 중앙 달력이 약 167일에서 약 **120일**로 준다(추정 = 91 / 0.8 + 추가분 약 6일).

* **두 번 시도 card와 재시도**: 재시도 비율은 약 10/26이다. 두 번 시도한 card는 4.4 h(b26pre)에서 15.3 h(P9, 밤 포함)까지 걸렸다. 이 비용은 h 실측 평균에 이미 들어 있다.

* **긴 실행**: B26-1 V3 2회 중앙 8.6 h, M10 82분, U-27b 약 22 h, 7a·7c SPICE(미측정).
* **design 작성**: Phase 3·4는 8~9회 검토를 거쳤다. 앞 Phase와 병렬로 쓸 수 있지만, 앞 Phase 병합본에서 사실을 다시 재야 해서(Phase 4 초안 HEAD 재측정 v0.2~v0.9.9) 일부가 임계 경로에 남는다.

### 4.3 작업 성격별 비중 (실측 + 추정)

* 지금까지(09-21 ~ 10-07): 새 엔진 기능 card는 0이다. 바뀐 줄은 code 1.7%, test 7%, 문서 22%, 판정 기록 68%다. agent 호출은 역할 agent 10%, 준비·검토·실측 90%다.
* 남은 일(card 수 중앙 기준, 추정): Phase 3는 이동·인프라로 20장(10%), Phase 4는 결함 수정(동작 변경)으로 52장(25%), 5~7c는 새 기능으로 136장(65%)이다. 모든 card에 같은 검증 절차(V1~V10, 승인, 판정 기록)가 붙는다. 그래서 2.4의 비율이 유지되면 남은 약 950 h 중 실제 엔진 코드 작성은 작은 몫이고, 나머지는 검증·조율이다.

## 5. 불확실성

* 5~7c의 card 수와 card당 시간은 외삽이다(1.1·3.1 식). 6a·7b는 알고리즘 신설이라 Phase 4 결함 수정보다 card당 시간이 클 수 있다(비관 쪽 위험).
* card당 시간 실측(4·6.7 h/card)은 표본이 작다(Phase 3 창 5장). 그 창에는 Phase 4 design 같은 다른 준비 작업도 섞여 있다.
* 달력 환산은 지난 4주의 근무 패턴(활동일 비율, 하루 10.5 h)이 그대로 간다고 가정했다.
* 사용자 공동분석(6a-2, UD-17)·승인 대기 시간은 기록에서 직접 잴 수 없다. 달력 추가분으로만 넣었다(추정).
