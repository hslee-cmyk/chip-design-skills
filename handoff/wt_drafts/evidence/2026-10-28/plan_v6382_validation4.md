## 2. 새 결함 검사 (a)~(d)

### (a) 경계 선언의 writer·저장 자리와 소비자 → **V4-1 (높음)**, V4-2 (중간)

**같은 키인가.** gain-budget :304와 oracle :510은 키가 같다. 둘 다 (시뮬레이터 판, 호환 모드(.spiceinit 내용 포함), 모델 파일 sha256)다. 그러나 다음은 하나로 묶이지 않았다.

1. **writer를 읽는 쪽으로 적었다.**
   - gain-budget :304는 'LUT 생성·엔진 bin 판정(D1)·card EO-1 oracle 넷리스트·card CPG-1 bench가 모두 이 선언을 READS'라고 적는다. OP-7 :510도 'LUT 생성 … 이 모두 읽는다'라고 적는다.
   - 그런데 D-4(:575)에서 선언을 쓰는 쪽은 둘이다.
     - 새 LUT: 생성 실행이 재서 meta에 쓴다(OP-8).
     - 기존 LUT: 검증자가 다시 재서 옆 선언 파일로 쓴다(OP-7).
   - 즉 LUT 생성은 writer다. 소비자 목록에 writer를 넣으면 '선언 하나, writer 하나'(graph 규칙 1의 정신)가 문언에서 흐려진다.
   - 고침: gain-budget :304·oracle :510에서 'writer = LUT 생성 실행(새 LUT, OP-8 meta) / 검증자 옆 선언(기존 LUT, OP-7), 소비자 = 엔진 bin 판정·oracle 실행 설정·CPG-1 bench'로 나눠 적는다. 저장 자리(LUT meta 칸·옆 선언 파일, G-14)도 gain-budget에서 한 번 가리킨다.
2. **OP-7과 WB-1 D1의 선후·소유가 없다.**
   - OP-7(oracle :510·:522)의 범위는 '엔진 파일 `E/lut/_helpers_bins.py`와 호출부, bin 규칙 선언을 읽는 경로'다. 선행은 OP-3, XRUN-F1 card C이고, D-4 승인 상태다.
   - WB-1 D1(:2240)도 같은 함수 `bin_index`를 고친다. 바꾸는 내용은 '격자 정수 비교 + 경계 방향은 선언에서 읽음'이다.
   - 실측: 엔진 `ebad06c1` `_helpers_bins.py`는 '아래 구간 우선' 고정 + 1 ulp 비교다. 선언 읽기는 없다(`grep bin_tie|bin_decl` 0). 즉 OP-7은 아직 구현되지 않았다.
   - WB-1 선행(:2251, 순서표 :1239)에는 OP-7이 없고, OP-7 순서에도 WB-1이 없다. 그래서 둘 중 하나가 일어난다.
     - WB-1이 먼저 병합되면 D1이 읽을 선언이 없다.
     - WB-1이 선언 읽기를 직접 구현하면 OP-7과 같은 규칙의 구현 자리가 둘이 된다(계획 간 둘째 생산자).
   - 고침(대안 비교):
     - (가) WB-1 선행에 OP-7을 넣는다. D1은 OP-7이 만든 선언 읽기를 재사용하고, 격자 정수 비교만 더한다.
     - (나) OP-7의 엔진 쪽 범위(선언 읽기)를 WB-1 D1로 옮기고, oracle 계획 OP-7은 옆 선언 측정·기록만 남긴다.
     - 권고 (가). 승인된 D-4/OP-7의 소유를 바꾸지 않는다. OP-7 선행인 OP-3은 EO-1 선행이라 어차피 WB-1 앞에 온다. 그래서 순서 비용은 OP-7 하나다.
3. **oracle 실행 설정·CPG-1 bench의 배선 card가 없다.**
   - gain-budget :304는 'card EO-1 oracle 넷리스트'가 읽는다고 적는다. 그러나 EO-1(:2021-)은 엔진 점을 oracle 입력 JSON으로 내는 생산자다. ngspice 호환 모드는 oracle 쪽 실행(`oracle_run`/`oracle_netlist`)이 정한다.
   - 실측: `tools/spice_oracle`에는 ngbehavior·.spiceinit가 0이다. 즉 기본 모드로 우연히 일치할 뿐, 선언을 읽지는 않는다.
   - oracle 계획에서 선언 읽기를 범위로 가진 card는 OP-7(엔진 파일만, :522)뿐이다. oracle 실행 설정 쪽을 고치는 card(OP-3 어댑터 또는 OP-8)에는 이 항목이 없다.
   - CPG-1 bench(`wt/_cmp_pilot/H/judge/spice_judge_base.py:20`, `wt/_cmp_pilot/judge/spice_judge.py:20`)는 둘 다 `SPICEINIT = "set ngbehavior=hsa\nset ng_nomodcheck\n"` 고정이다.
   - '만들면 배선' 기준으로 소비자 넷 가운데 둘(oracle 실행, CPG-1 bench)의 배선 주체가 없다.
   - 고침:
     - oracle 쪽: 'oracle 어댑터가 LUT 선언의 호환 모드로 실행한다(다르면 거부)'를 OP-3 또는 OP-8 범위·완료 조건에 넣는다. oracle은 이미 `process.lut_npz` meta에서 코너·온도를 읽으므로(`oracle_netlist.py:31-32`) 같은 경로로 읽는다. NFR-P3(:100, 파일로만 공유)과 충돌하지 않는다.
     - CPG-1 쪽: V4-4에서 다룬다.

**V4-2 (중간) oracle D-4·G-14 옛 문언과 승인 결정 문언 변경 표지.**
- D-4(:575)는 스스로 '이 항목이 정본 하나'라고 적는다. 그런데 아직 '기본 방향은 … 모델 파일 sha256 묶음 + 생성 시뮬레이터 판', '근거는 모델 파일 sha256 + 시뮬레이터 판에 묶는다'로 남아 있다.
- G-14(:601)도 '규칙은 (모델 파일 sha256 묶음, 시뮬레이터 판)에 묶고'로 남아 있다.
- OP-7(:510)만 넓혀서, 정본 행(D-4)과 card 행(OP-7)이 다른 키를 말한다.
- D-4는 승인 결정(O-1)이다. 그 키와 읽는 쪽(oracle 실행 설정·CPG-1 bench 추가 -- 옛 D-4는 '엔진은 이 선언만 읽는다', PC-9 '오라클 능력 아님')을 넓히는 것은 결정 문언 변경이다.
- 그런데 oracle history v0.6.19 둘째는 '새 사용자 결정 아님(전파)'이라고만 적는다.
- 고침: D-4·G-14를 같은 키로 고치고, history에 'D-4(승인 O-1) 문언 변경 -- 키에 호환 모드 추가, 읽는 쪽에 oracle 실행 설정·CPG-1 bench 추가'와 옛 문장을 적는다.
  - 내 판단으로 이것은 '원래 취지와 다름'은 아니다. D-4의 취지 '경계 소속 = LUT를 만든 실행의 동작'을 정밀하게 만든 것이다.
  - 다만 승인 결정의 문언 변경이므로 승인 질문 목록에 올린다.

### (c) m·w_f 정본 필드와 기존 W 필드 → **V4-5 (중간)**

- :304가 정한 것: '실현 총 폭 정본 = m·w_f(격자 반올림 뒤) -- 손가락 필드의 성분 하나'. 소비자는 면적·용량·잡음·mismatch·DC 재평가·넷리스트·고정점 수렴이다. writer는 커널 W 계산 블록 하나다. 여기까지는 맞다(둘째 생산자 없음).

  - 같은 행 앞 문장: '출발 단계에서 그 함수가 낸 W·w_f는 출발값(EP-7 -- **커널 봉인 W**와 정의 축이 다른 양)'. 여기서 커널 W는 봉인 필드다.
  - 뒤 문장: 'm·w_f ≠ W의 차는 **출발값과 실현값의 차**로 기록(EP-7)'. 여기서 커널 W는 출발값이다.
- EP-7(:114)은 '판정과 출발값 구분'이다. 커널 안의 W가 출발값이면 봉인 스냅샷의 W 필드는 무엇인지, 남는다면 소비자가 누구인지 정해야 한다. 소비자 후보: N3.6 봉인 불변식, gds·gmb 환산, as-built `caps(…, op.W)`.
- 고침:
  - W를 고정점 블록 안 지역값으로 내린다(graph 필드 아님).
  - 또는 W를 남기되 정의 축('격자 반올림 전 요구 폭')과 소비자를 적는다(graph 규칙 3).
  - '차의 기록' 자리를 정한다. 결과 JSON 출력 전용인지 적고, 엔진 계산은 그 차를 읽지 않는다고 적는다.
  - 'DC 재평가가 m·w_f를 읽는다'가 어느 계산 틀인지 한 줄 적는다. θ 고정 사이징인지, W 고정 KCL 섭동(계산 틀 원칙)인지다. 격자 반올림 뒤에는 ID(m·w_f) ≠ I이기 때문이다.
