## 2. 선택지별 평가

### A. 도구 수정 없이, 시도마다 한 번, harness 밖 Windows 분리 프로세스(파일로 추적)

* **증거 무결성**: 최상. base 판 도구 원출력 그대로(carry check의 `len(run) == mutants`, id 중복 0, `survivor_bindings` 그대로). 판정 규칙·도구 불변.
* **규칙**: 사용자 memory '장시간 실행은 run_in_background, 수동 `&`·`nohup` 금지'와 브리프 §0.3의 예외 → **사용자 승인 1건**(1차·2차 두 실행을 한 질문에). harness는 `run_in_background` 대기 명령(< 2 h, 반복)으로 rc 파일·PID를 보므로 'harness가 추적한다'는 취지는 유지된다.
* **거짓 killed(부하·timeout)**: 직렬이라 자기 부하는 1 프로세스. 위험은 **같은 기계의 다른 agent pytest**(memory의 '동시 agent 6~8' 운영과 충돌)와 **절전**. 생존 변이 155~263 s 대 상한 600 s → 여유 2.3배. 1차의 U3 생존이 거짓 killed가 되면 carry check(`survivors` 1개)가 멈춰 **드러난다**. 2차는 기대 생존 0이라 진짜 생존이 timeout으로 가려지면 **거짓 PASS**가 된다 → `--out`의 `"exit": "timeout"` 레코드를 전부 따로 재현해 무한 루프인지 확인(런타임 문서 §5-6, 이미 계획).
* **결정성**: 기존 직렬 도구와 같다.
* **Windows 생존**: 1.3 -- harness 트리 밖 확인, 세션 종료 생존은 미시험, 재부팅·로그오프 시 처음부터(`--out` 지움). 실행 중 절전 금지 필요. WMI로 띄운 프로세스는 harness 환경 변수를 물려받지 않으므로 래퍼 `.cmd`에 TMP·TEMP·TMPDIR·PYTHONPYCACHEPREFIX·APPDATA·PYTHONIOENCODING을 리터럴로 적는다.
* **비용**: 1차 2.1/4.3/5.5 h + 2차 같음 = **4.2 / 8.6 / 11.0 h**(임계 경로). 그 동안 게이트는 B26-1 전용이라 다른 card 병합은 못 하지만 다음 card 초안·키트 준비는 병렬 가능(단 부하 주의). 시도가 하나 더 늘 때마다 +2.1~5.5 h.

### B. 먼저 게이트 card(`--jobs`·`--resume`), 그 뒤 V3

* **증거 무결성**: 변경 뒤 도구 원출력이라 판정 근거로 유효. 단 **새 도구 자체의 정확성**(직렬과 같은 결과)이 그 card의 redteam·V10으로 증명돼야 한다 -- 계약 후보: 같은 입력에서 `--jobs 1`과 `--jobs N`의 판정 JSON·`--out` 레코드 집합(순서 무관) 같음, `--resume`은 머리(base·head·도구 판 해시·인자)가 다르면 거부, 이미 있는 id 건너뜀·판정은 `--out` 전체에서 다시 계산, 변이 id·`bind_hash`·`targets_by_def` 불변(B26-1 기록 5가 이것에 묶임).
* **규칙·절차**: gate card 한 장 = 초안(+ design 05 §10 V3 ④ 문구 검토 -- '변이마다 격리 복제본'은 N개 복제본과 맞음, 고칠지는 검토 몫) → **사용자 승인 기록**(gate change, `target_kind: diff`) → 순서 0(doc·spec·승인 커밋, push) → redteam 공격 데이터(test) → code → merge → audit(V1 = pytest + redteam 전체) → push. 선례 1회 시도·승인 1건·검토 0~3회.
* **B26-1 되돌리기**: 지금 역할 브랜치 3개가 있어 B 게이트 card는 순서 0 push부터 막힌다(EL1 `_judge_push`, 한 번에 변경 하나). 또 V 도구는 **base 판**을 쓰므로(브리프 '게이트 코드 = base 판', design 05 §12-7) 1차 시도의 base가 새 도구를 담아야 한다 → **현재 1차 시도를 정리하고 B1' = 새 master에서 다시 시작**. T1(`c247a76`) 내용은 정리 전에 `git show`로 보관하면 test-author가 show→Edit로 같은 blob을 다시 만든다(2차 시도와 같은 방식, 설계 다시 하지 않음). 새 도구가 test·P9 base blob을 안 바꾸므로 V5 diff_hash는 같은 값이 다시 나온다. 버리는 일: T1 작성(약 1 h, 13:39 spec push → 14:39 T1)과 진행 중인 순서 3.
* **"T1을 꼭 다시 해야 하나"**: B를 1차 V3에 쓰려면 **예**(위 두 이유 -- 브랜치가 있는 한 B card가 gate에 못 들어가고, 들어가도 1차 base B1 = `6df4bd7`의 도구는 옛 판). T1을 살리면서 새 도구를 1차에 쓰는 길은 '1차 측정만 base 아닌 판 도구'라는 예외(승인 필요)인데, 그래도 B card를 gate에 넣으려면 B26-1 브랜치를 지워야 해서 T1 브랜치는 어차피 사라진다 -- 실익 없음.
* **G1 합성**: B card가 G1 앞에 들어가면 G1 spec·시제품·키트를 다시 맞춰야 한다(1.4). G1 뒤로 미루면 B26-1에 도움이 없다(G1은 B26-1 뒤).
* **거짓 killed**: N개 동시 실행은 자기 부하를 N배로 만든다. 18 코어에서 N = 4~6이면 생존 변이 600 s 여유는 남을 것(추정 -- 12개 병렬 모의는 CPU 합 20.9 h / 벽시계 1.75 h ≈ 11.9배로 거의 선형이었다, B26-1 card '두 번 시도 절차' 예상 비용). 다른 agent 부하가 겹치면 A보다 위험하다. N 상한과 timeout 레코드 재현을 계약에 넣어야 한다.
* **병렬 결정성**: 복제본별 작업 디렉터리는 분리되지만 (i) pytest 기본 `--basetemp`(`%TEMP%/pytest-of-<user>/pytest-<n>`, 최근 3개만 남기고 지움)를 worker가 공유하면 서로 지울 수 있다 → worker마다 TMP 분리 필수, (ii) `PYTHONPYCACHEPREFIX` worker별, (iii) 기준 실행 캐시(`baseline_ok`)를 worker 간에 어떻게 나눌지(앞 단계에서 인벤토리 기준 실행을 병렬로 먼저 끝내는 구조가 단순), (iv) APPDATA·LUT 캐시 등 저장소 밖 공유 상태 -- 미조사(그 card 작성 전 실측 몫). `PYTHONHASHSEED`는 지금도 고정하지 않으므로 직렬과 같은 조건.
* **비용**(추정): 초안·검토 3~8 h(B28 2.7 h보다 큼 -- 병렬·resume·결정성 계약), 승인 대기(사용자 응답 시간, 미지), gate 사이클 2~8 h(선례), B26-1 1차 다시 시작 1.5~2.5 h, G1 다시 맞춤 2~6 h, 그 뒤 V3 1회 약 0.45 / **1.0** / 1.3 h(N = 6, 부하 계수 1.3 가정 -- 추정: 기준 실행 75분/6 + 변이 3.0 h/6, × 1.3).

### C. 혼합 -- 1차는 A로 지금, B card는 병렬로 준비해 2차부터 새 도구

* **2차 base B2에 새 도구가 들어가는가**: carry `final`은 `HEAD^ = B1`·`gate/master = B1`을 단언하고(carry.sh 561~563행), `after-push`는 `gate/master = C`를 단언한다(578행). 그래서 B card는 **운반 push(C)와 after-push 뒤, 2차 순서 1 전**에만 gate에 들어갈 수 있다(그 사이 역할 브랜치 0이라 EL1이 허용). 그러면 2차 base = B2' = (C + B card 병합·판정 기록)이고, 2차 auditor의 V 도구는 B2' 판 = **새 도구**다. 맞다.
* **1차 산출물·운반 해시 유효성**:
  * V5 기록 4 target(`diff_hash`) = `weakening_diff.py`가 (경로, base blob, head blob)로 낸 값 -- B card가 `weakening_diff.py`·test 파일을 안 바꾸면 **그대로 유효**(after-push가 쓰는 `approved_hashes(r, b2)`도 B2' 트리에서 같은 기록을 찾는다).
  * V3 기록 5 target(`<변이 id>@<def 묶기 해시>`) -- 묶기 해시는 `ast.dump(def)` sha256로 carry가 도구와 따로 계산해 대조하고(carry.sh 279~287행), 변이 id = AST 노드 경로. B card가 `bind_hash`·변이 생성·id 형식을 안 바꾸면 **유효**(B card 계약으로 고정해야 한다). K2의 그 def가 K1과 글자까지 같아야 한다는 조건은 그대로.
  * 1차 `attempt1_v3.json`(옛 도구)과 2차 V3(새 도구)가 한 판정 기록에 함께 실린다 -- 각 시도가 자기 base 판 도구를 썼으므로 규칙 위반은 아니나 basis에 두 도구 판을 적어야 한다. '대상 수·def별 targeted가 1차와 같아야 한다'(브리프 4.6 V3 행)는 B card가 대상 선택을 안 바꾸면 성립.
  * **고쳐야 할 문서**: 브리프 4.1 ⑦ `git diff --quiet <carry B2> <새 B2> -- skills tools workspaces`는 tools가 바뀌므로 **반드시 실패** → 'B card 경로만 다름' 확인으로 바꿔야 한다. spec card '두 번 시도 절차' 단계 3 "base B2 = 2의 master"·carry `after-push`가 상태 파일에 적는 `B2=`도 B2'와 다르다 → card 개정(문서 커밋) 또는 '2차 착수 때 gate master로 읽는다'는 브리프 문장(4.1 ⑦에 이미 같은 모양의 문장이 있다) 확장. 2차 auditor 캐시 old = B2'.
* **T1을 다시 할 필요**: C에서는 **없다**(1차는 B1·옛 도구 그대로, 2차는 원래 계획대로 운반 blob `cp` + T1.patch show→Edit).
* **G1 합성**: B card가 G1 앞이므로 B와 같이 G1 다시 맞춤 필요.
* **효과**: B26-1 2차 V3가 4.3 h → 약 1.0 h(추정), M10 82분 → 약 20~25분(추정). 대신 B card의 gate 사이클(2~8 h)이 1차와 2차 사이 임계 경로에 들어간다(그 사이 gate는 B card 전용). B card 초안·검토는 1차 V3가 도는 동안 병렬로 할 수 있어 임계 경로 밖.

## 6. 불확실성 정리
* V3 단가는 부하 통제 없는 29변이 표본·인벤토리 실측이고 K1 대상 분류 없이 잰 것(런타임 문서 §2.3 주의). 실제 B26-1 1차가 첫 실측이 된다.

* W(비-V3 작업)는 card 종류별 선례 범위로 잡은 **추정**이며, 사용자 답 대기(T0·T1·F1 V5, D0b D-11 재질문 가능성, 이 A 예외 질문)·밤·쉬는 날·재시도를 넣지 않았다. 실제 달력 시간은 이보다 길다.
* 분리 프로세스의 세션 종료 생존·절전 동작은 미검증(1.3).
