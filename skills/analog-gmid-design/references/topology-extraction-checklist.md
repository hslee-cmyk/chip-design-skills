# topology.json 추출 체크리스트 (스펙/회로도 → topology library JSON)

> 방법론 배경은 `gm-id-methodology.md`가 아니라 이 문서 자체가 정본이다 — "이미 만들어진
> topology.json을 어떻게 사이징하나"(→ `function-selection-map.md` §10, do.md 배치 7)와는
> **다른 문제**: "논문/스펙/회로도 이미지에서 topology.json 자체를 어떻게 처음 만드나."
>
> 이 문서는 가상의 위험이 아니라 **실제 사고 사례**(아래 §1)에서 나왔다 — 상세 경위는
> `current_reuse_telescopic_ota.topology.json`의 `_correction_log`/`_correction_log_2` 필드와
> `sky130-worked-example.md` §13/§13.5, `consistency-map.md` 47차/48차 항목 참고.

## 1. 왜 이 체크리스트가 필요한가 (실제 사고 요약)

`current_reuse_telescopic_ota` topology.json 작성 중 실제로 발생한 5개 오류(전부 사용자가
직접 재확인해서 잡음 — harness나 사전 게이트가 없었다):

| # | 오류 | 근본 원인 | 발견 방식 |
|---|---|---|---|
| 1 | Fig.4(설명용 참고 다이어그램)를 실제 회로로 오인, 가상의 소자 9개를 topology.json에 넣음 | 부록(Appendix)을 처음에 안 읽음 + 본문의 "Figure 3" 오탈자(실제로는 Figure 2)를 그대로 믿음 | 사용자가 논문을 처음부터 끝까지 다시 읽으라고 지시 |
| 2 | Vop측 Class-AB 소자 12개 통째로 누락 | 회로도 전체(Fig.1)를 안 보고 Fig.3(Vom측만)만 보고 완료로 판단 | 사용자가 "회로도를 그림으로 다시 읽어라" 지시 후 발견 |
| 3 | M9a/M18a 극성(nmos↔pmos) 오류 | 저해상도 이미지만 보고 판단, DC 동작점 데이터(id 부호) 대조 안 함 | 사용자가 Appendix Fig.7의 id 부호를 직접 대조 |
| 4 | M57/M58의 "vdd" 라벨을 독립 소스 연결로 오독(실제로는 well/body bias 태그) | 반복되는 텍스트 라벨을 그래프 구조와 교차검증 안 함 | 사용자가 고해상도 이미지+직접 설명으로 정정 |
| 5 | M57 gate를 "Vip"로 오독 | 저해상도 이미지에서 인접 라벨 혼동 | 사용자가 고해상도 이미지로 재확인 |

**공통 패턴**: 전부 "AI가 한 번 읽고 확정 → 나중에 사용자가 우연히 다시 확인해서 발견"이었다.
이 문서의 목표는 이 순서를 뒤집는 것 — **확정하기 전에 구조적으로 검증 가능한 것부터
자동으로 걸러내고, 사람에게는 걸러지지 않은 항목만 묻는다.**

## 2. 완전 자동추출은 안 된다 (먼저 인정할 것)

이미지 기반 회로도 판독은 harness 함수 하나로 신뢰성 있게 자동화할 수 있는 문제가 **아니다**:
- 저해상도 이미지의 라벨 오독은 알고리즘으로 못 잡는다(사람이 고해상도로 다시 봐야 한다).
- 도면 컨벤션의 모호성(예: PMOS의 "vdd" 라벨이 소스 연결인지 well/body bias 태그인지)은
  회로마다/설계자마다 다를 수 있어 일반 규칙으로 완전히 해소 안 된다.
- 원문 자체의 오탈자("Figure 3"가 "Figure 2"의 오타)는 구조로 잡을 수 없다.

**따라서 이 체크리스트는 "사람 확인을 없애는" 방법론이 아니라 "사람이 확인해야 할 항목을
좁히는" 방법론이다.** 아래 §3~§6이 그 절차.

## 3. Stage 0 — 원문 완전성 체크 (추출 시작 전, 실행 순서 고정)

- [ ] 문서 전체 페이지 범위 확인 — **본문+부록 전부**, 스킵 금지(사고1의 원인).
- [ ] 각 Figure를 "실제 회로 스키매틱" vs "설명용 참고 다이어그램"으로 먼저 분류 —
      **캡션만 보지 말고 본문 텍스트에서 그 Figure를 언급하는 문장을 grep해서 대조**
      (사고1: 캡션은 "Schematic of the biasing circuit"라 실제 회로처럼 보였지만, 본문은
      "예제/설명용"이라고 다른 문장에서 밝히고 있었다).
- [ ] 소자 개수가 텍스트에 명시적으로 언급되면(예: "9-transistor", "12 devices") 기록해
      뒀다가 Stage 2의 체크섬으로 쓴다.
- [ ] 회로 전체가 몇 개의 하위 블록(1단/2단/bias-gen/CMFB 등)으로 구성되는지 목차/섹션
      구조에서 먼저 확인 — 이 목록과 실제로 추출한 블록 목록을 나중에 diff한다(사고2 방지).

## 4. Stage 1 — Figure별 반복 추출 + 즉시 감사 (한 번에 다 하지 않는다)

- [ ] Figure 하나(또는 하나의 기능 블록)만 먼저 추출해 draft netlist에 추가한다.
- [ ] **그 자리에서 바로** `find_matching_candidates()`/`find_hub_merge_candidates()`를
      draft 전체(지금까지 추가된 것)에 실행한다 — 전체 추출이 끝난 뒤 한 번만 하지 않는다.
- [ ] fully-differential 회로라면, 방금 추가한 블록이 "반쪽"만 있는 건 아닌지 확인 —
      differential/mirror 구조인데 대응하는 반대쪽이 아직 없으면 그 자체가 정상(다음 Figure에서
      채워질 예정)일 수도 있으니, **Stage 0에서 적어둔 하위 블록 목록과 대조**해서 "이 블록은
      원래 이 Figure 하나로 끝나는가, 다른 Figure에 나머지 절반이 있는가"를 판단한다(사고2는
      이 대조를 안 해서 "끝났다"고 잘못 판단한 경우).

## 5. Stage 2 — 자동 이상탐지 게이트 (신규 harness 함수, 사람에게 묻기 전에 실행)

**제안 함수**: `detect_extraction_anomalies(draft_json: dict, source_text: str, expected_counts: dict[str, int] | None = None) -> list[Anomaly]`

| 체크 | 방법 | 사고 대응 |
|---|---|---|
| 대칭성 기대치 위반 | `find_matching_candidates()` 결과를 kind/net별로 세어, 짝이 안 맞는(홀수이거나 기대한 개수와 다른) 그룹 flag | 사고2(Vop 12개 누락) |
| 매칭쌍 kind 불일치 | `matching_pairs`로 확정된 쌍인데 `kind`(nmos/pmos)가 서로 다르면 flag(단, Monticelli 상보쌍처럼 의도된 경우는 override 필요) | 사고3(M9a 극성) |
| net 참조 카운트 1(dangling) | 한 device만 참조하는 net을 전부 나열 — 오독 가능성 있는 net 이름 후보 | 사고4/5(net 이름 혼동) |
| 텍스트-숫자 대조 | `expected_counts`(Stage 0에서 기록한 텍스트 언급 개수)와 draft의 실제 개수 diff | 사고1(가상 소자 9개, 실제와 개수 자체가 다름) |
| 라벨-구조 교차검증(선택) | 반복되는 동일 라벨(예: "vdd")이 여러 소자의 **같은 필드**(source)에 나타나면, 그게 실제 소스 공유인지 다른 의미(well/body bias 태그)인지 draft 작성자가 명시적으로 확인했다는 플래그가 있는지 확인 — 없으면 flag | 사고4 |

- [ ] Stage 1에서 블록을 추가할 때마다 이 함수를 실행한다(전체가 끝난 뒤 한 번이 아니라).
- [ ] flag된 항목이 0개가 될 때까지 다음 Stage로 넘어가지 않는다(단, Stage 3에서 사람이
      "확인했고 의도된 것"이라고 명시적으로 해소하는 것도 0개로 치는 방법 중 하나).

## 6. Stage 3 — 선택적 인간 확인 (전부가 아니라 flag된 것만)

- [ ] Stage 2에서 flag된 항목만 정리해 목록으로 만든다 — "51개 소자 전부 확인해달라"가
      아니라 "이 5개만 확인해달라"는 형태로 좁힌다.
- [ ] 각 flag 항목에 대해 **고해상도 이미지 + 구체적 질문**(예: "M57과 M58의 gate가 어디에
      연결됩니까, 두 후보 A/B 중 어느 쪽입니까")으로 확인 요청 — 모호하게 "이거 맞아?"라고
      묻지 않는다.
- [ ] 확인된 답변은 draft에 반영하고, **왜 원래 추측이 틀렸는지**를 `_correction_log`류
      필드에 남긴다(다음에 같은 실수를 반복하지 않도록 — `known-incidents.md`와 같은 취지).

## 7. 구현 방식 제안 — 멀티에이전트 Workflow

이 파이프라인은 `Workflow` 도구의 "multi-modal sweep + adversarial verify" 패턴과 맞는다:

1. 전체 문서 스캔 에이전트 — Figure 분류(실제 회로 vs 설명용) + 텍스트 언급 소자수 추출(Stage 0)
2. Figure별 병렬 추출 에이전트 — 고해상도 크롭 이미지 → device list JSON(Stage 1)
3. merge + net-name 충돌 해소 단계
4. `detect_extraction_anomalies()` 게이트(Stage 2)
5. flag된 것만 사용자에게 질문(Stage 3)

구현 우선순위는 do.md의 별도 배치(사이징 harness인 배치 7과는 분리) 참고.

## 8. 정직한 한계 (재강조)

- 이미지 해상도/도면 컨벤션의 모호성은 알고리즘으로 완전히 제거 못 한다.
- `detect_extraction_anomalies()`가 "0개 flag"를 반환해도, 그건 "구조적으로 검증 가능한
  범위 안에서 이상 없음"이지 "100% 정확함"이 아니다 — 원문 자체의 오탈자나 라벨 관례처럼
  구조로 못 잡는 오류는 여전히 남을 수 있다.
- 이 체크리스트의 목표는 사람 확인을 0으로 줄이는 것이 아니라, 51개에서 flag된 소수로
  줄이는 것이다.
