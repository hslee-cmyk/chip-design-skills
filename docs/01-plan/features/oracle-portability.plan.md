# oracle-portability Planning Document

> **Summary**: SPICE 오라클(`skills/analog-gmid-design/tools/spice_oracle/`)을 **시뮬레이터 무관·공정(PDK) 무관**으로 바꾼다. 구조는 세 층이다.
> 1. **오라클 코어**: 회로 IR, 측정 정의, 판정·비교 수학. 시뮬레이터와 PDK를 모른다.
> 2. **시뮬레이터 어댑터**: IR을 방언 넷리스트로 쓰고, 실행하고, 결과를 읽어 정규화한다. 자기 능력을 선언한다.
> 3. **PDK 기술자**: 오라클 전용 선언 파일이다. 엔진 `gmid_pdk_decl/1` 선언 파일을 경로·sha256으로 참조하고(엔진 파일·로더는 바꾸지 않음, D-9), 모델 호출 형식, include, 코너, 온도, MC 불일치 켜는 법, 확산 규칙, op 파라미터 이름, bin 경계 규칙을 담는다.
>
> 그리고 **공정 무관 오라클 능력 확인**(T-31)을 이 계획이 소유한다. 어떤 (PDK, 시뮬레이터) 조합에서 MC 불일치·온도 의존이 실제로 동작하는지 재는 절차, 기록 형식, fail-closed 규칙이다. offset-trim 계획(v0.5 N3.9)은 이것을 의존으로만 쓴다.
>
> 첫 어댑터는 ngspice, 첫 PDK는 sky130이다. 둘 다 **사례일 뿐**이고 규칙에는 이름을 넣지 않는다.

## N0. 문서 안내

* **담는 것**: 목적·범위, 확정 결정, 요구, 3층 구조와 규칙, 능력 확인 절차, 재작성 범위·삭제 목록, 상위 문서 개정 목록, card 분할과 완료 조건, 위험, 원문 근거, 열린 결정.
* **담지 않는 것**: 경위와 조사 과정. history에 둔다.
* **값 원칙**: 이 문서에는 수치 상수를 두지 않는다. 허용 폭은 시뮬레이터가 선언한 해 정확도(입력 `testbench.options`, 없으면 어댑터가 출처와 함께 선언한 기본값)나 MC 표본 수에서 유도한다. PDK 값은 PDK 원본 파일에서 기술자가 계산한다.
* **이름 원칙**: 규칙·코어 코드·판정에 회로·PDK·시뮬레이터 이름을 넣지 않는다. 이름은 '사례' 표기로만 쓴다.
* **인용 규칙**: 코드는 `파일:줄`, 기준은 base `d783efe`다. `O/` = `skills/analog-gmid-design/tools/spice_oracle/`, `E/` = `skills/analog-gmid-design/gmid_engine/`, `A/` = `skills/analog-gmid-design/assets/`.
* **오케스트레이터 기본안**: 사용자 결정·상위 문서가 정하지 않은 것을 이 계획이 정할 때 '(오케스트레이터 기본안)'으로 표시한다. 사용자가 바꿀 수 있다.

## N1. 목적·범위·요구

### N1.1 목적

사용자 취지(2026-10-16): gm/ID의 장점은 **작은 노력으로 SPICE와 작은 오차로 빠르게 설계**하는 것이고, 이것이 이번 개발의 가장 큰 이유다. 그 '작은 오차'를 재는 장치가 SPICE 오라클이다(상위 DEC-72 모델 오차, N3.8 `verified_by`). 오라클이 한 시뮬레이터·한 PDK에 묶여 있으면 다른 fab에서는 엔진 결과를 판정할 수 없다(T-31 "다른 fab에서도 사용할 수 있으니까").

이 기능의 목표는 둘이다.
1. 오라클 판정 로직이 시뮬레이터·PDK를 모르게 한다. 새 시뮬레이터는 어댑터 하나, 새 PDK는 기술자 파일 하나로 붙는다(T-33).
2. 어떤 (PDK, 시뮬레이터) 조합에서든 MC 불일치·온도 의존이 실제로 동작하는지 확인하는 절차를 두고, 확인되지 않은 조합에서는 그 판정을 거부한다(T-31).

### N1.3 기능 요구

| ID | 요구 |
|---|---|
| FR-P1 | **코어 무방언**: 코어 모듈 집합(`O/core/`, N0.1)은 시뮬레이터 방언 토큰과 PDK 이름을 갖지 않고, 금지 모듈(어댑터 패키지, `subprocess`)을 import하지 않는다. 토큰 목록은 **검증자가 소유**하고 **문법 형태**로 정의한다(완료 조건 1, G-8) |
| FR-P2 | **회로 IR**: 본 회로와 모든 파생 테스트벤치(β 루프, 개루프 pz, noise, MC, 스윙, iso, ratio·rout)를 IR에서 만든다. 넷리스트 텍스트를 다시 파싱하는 경로는 없다(N3.0 F-4) |
| FR-P3 | **어댑터 계약**: `write(IR, 요청) → 실행 → 정규화 결과`. 극성 정규화, 내부 벡터 이름 대응, 오류 분류, 실행 캐시 키, 능력 선언을 어댑터가 맡는다 |
| FR-P4 | **PDK 기술자**: 오라클 전용 기술자 파일이 오라클이 쓰는 PDK 사실을 담는다(N3.4). 엔진 선언 파일은 sha256으로 참조만 하고 고치지 않는다(D-9). 원본 PDK 파일 경로·sha256은 **파일마다 정본 한 곳**이다(N3.4, O-3): 엔진 선언에 있는 파일은 엔진 선언이 정본이고, 없는 파일만 기술자 `extra_sources`가 정본이다. 기술자는 sha256이 맞을 때만 원본 경로를 쓴다. 읽는 코드는 공유하지 않는다(오라클 C1: 엔진 import 금지) |
| FR-P5 | **능력 확인**(T-31): 절차·확인 항목·기록 형식(N3.5). 유효한 능력 기록이 없는 조합에서는 MC 판정·온도 범위 판정·온도 보정 루프를 거부한다(fail-closed). 공칭 판정에는 능력 기록을 요구하지 않고 실행마다 자동 대조(모델 묶음 sha256)를 한다(D-7) |
| FR-P6 | **동일성**: ngspice 어댑터로 돈 오라클 결과가 기준선과 같다(N4 비교 칸·허용 기준) |
| FR-P7 | **조기 종결 위치**(D-1): 판정 규칙은 코어가 정의하고, 시뮬레이터 안 조기 종결은 어댑터 능력이다 |

| FR-P9 | **보고**: 오라클 결과 JSON에 어댑터 이름·버전·실행 파일 지문, 기술자 지문, 능력 기록 id를 적는다 |

### N3.1 3층 구조와 경계

```
오라클 코어 (시뮬레이터·PDK 모름)
  입력 검증 · 회로 IR 생성(본 회로 + 파생 테스트벤치) · 해석 요청 · 판정·비교(oracle_compare)
  · 안정성 수학(Nyquist, 창 판정, 조기 종결 규칙, RHP 집계, tran 계획) · 잡음 밀도·적분 · MC 표본 설계·입력 환산
  · 스윙 경계 탐색 · C15 topology 대조(IR 기준) · 능력 확인 절차의 벤치 IR과 판정
        │ IR + 해석 요청[]                ▲ 정규화 결과
        ▼                                 │
시뮬레이터 어댑터 (사례: ngspice)
  방언 쓰기 · 실행 · 결과 읽기 · 내부 벡터 이름 대응 · 극성 정규화 · 오류 분류 · 캐시 키 · 능력 선언·보정값
        ▲ 모델 호출 형식, include, 코너·온도 지정, MC 방법, op 파라미터 이름 집합
PDK 기술자 (사례: sky130; 오라클 전용 파일, 엔진 gmid_pdk_decl/1 선언을 sha256으로 참조)
```

**경계 규칙**:
1. 코어(`O/core/`)는 어댑터 패키지(`O/adapters/` 아래 모든 모듈)와 `subprocess`를 import하지 않는다. 진입점이 선택된 어댑터를 주입한다. 프로세스 실행은 어댑터만 한다.
2. 어댑터는 판정하지 않는다. 판정에 필요한 분해능(해 정확도)은 값으로 넘긴다.
3. 기술자는 데이터다. 기술자에 코드(식 평가 외)를 넣지 않는다. 식은 `gmid_pdk_decl/1`의 '원본 파일 값으로 계산하는 식' 형식을 따른다.
4. 시뮬레이터 결함 회피(예: pz 거짓 RHP 극)는 두 부분으로 나눈다. **코어**는 '극점 결과는 독립 증거(개루프 과도)로 확인될 때만 판정에 쓴다'는 일반 규칙을 갖고, **어댑터**는 pz 능력과 그 신뢰 범위를 선언한다. 어느 쪽이 회로 이론 규칙이고 어느 쪽이 회피책인지 design이 항목마다 적는다(G-3).

### N3.2 회로 IR·해석 요청·정규화 결과

* **IR이 만드는 것**: 본 회로(free/forced/iso), β 루프, 개루프 pz, noise, MC 래퍼, 스윙 servo 이동, ratio·rout 여기, C10 과도 테스트벤치. 지금 텍스트 재작성으로 하던 변형(F-4)은 전부 IR 변환으로 한다.
* **이름 규칙**: 원소 이름 접두사(지금 `X`, `Rp_`, `Vsrc_` 등)는 방언 규약이라 어댑터가 정한다. IR은 원소 종류를 필드로 갖는다. 대소문자 충돌 검사(지금 넷 이름 대소문자 무시 전제)는 어댑터 능력(`case_insensitive_names`)으로 선언하고, 코어는 선언에 따라 충돌을 거부한다.
* **결과 키**: 소자 값은 IR 소자 이름, 넷 값은 IR 넷 이름으로 돌아온다. 잡음 기여도 IR 소자 이름 기준이다(F-8의 내부 경로 해석은 어댑터 + 기술자 모델 호출 형식이 한다).
* **오류 분류**: 어댑터가 로그를 공통 코드로 바꾼다(예: 수렴 실패, 특이 행렬, 시간 걸음 실패, 시간 초과, 모델 없음). 코드 집합은 G-4.
* **형식 정본**: IR·요청·결과의 스키마는 design이 정한다(G-1, G-2).

### N3.3 어댑터 능력 선언과 C10 조기 종결(D-1)

* 어댑터는 능력 목록을 선언한다. 후보(ngspice 기능에서 거꾸로 뽑은 것이라 확정 목록은 G-3): 창 단위 조기 종결(실행 중 조건부 정지·재개), pz, 네이티브 MC 표본 실행(기술자가 선언한 불일치 켜는 법으로, 표본 시드·표본 정체 보존·소자별 독립 여부 선언), AC 여기 전환, 온도 지정, op 스윕, 잡음 기여 분해, 극성 정규화가 정의된 모델 계열.
* 보정값: 기본 허용오차(지금 `_NGSPICE_DEFAULT_TOL`, 출처는 그 시뮬레이터 문서 기본값), 데이터 자릿수(지금 `WRDATA_NUMDGT`), 창당 실행 시간 상한(지금 `oracle_config.json`). 측정 조건·코퍼스·출처를 함께 선언한다. 상한 보정값이 없는 어댑터에서는 C10 과도가 사용자 `--timeout-s` 없이는 거부한다(오케스트레이터 기본안, `adapter_calibration_missing`).
* **D-1 권고**: C10 판정 규칙(f_crit, n_pp, tmax, 창 판정 g↑·g↓, 조기 unstable, 한계 사이클)은 코어가 정의한다. 시뮬레이터 안 조기 종결은 어댑터 능력이다. 능력이 있으면 어댑터가 코어 규칙을 방언으로 옮겨 시뮬레이터 안에서 멈추고, 코어는 지금처럼 파일로 같은 기준을 다시 검증한다. 능력이 없으면 전체 창을 실행하고 코어가 같은 기준을 사후에 적용한다.
  * '결과 동일'의 범위: 전체 창 실행이 끝까지 가면 판정 상태(`unstable`·`stable` 등)가 같다. 다만 조기 종결은 원래 GHz 진동 회로가 끝나지 않는 문제(계약 §0)를 막으려고 생겼다. 능력이 없는 어댑터에서 그런 회로는 시간 상한에 걸려 `failed`가 될 수 있다. 이때도 PASS 불가라는 판정 결론은 같지만 상태 이름은 다르다(X-2).
  * **검토할 대안(재실행 방식)**: 능력이 없는 어댑터에서도 창 j를 끝낼 때마다 tstop = t_end + j·W로 늘려 처음부터 다시 실행하고, 코어가 매번 조기 unstable 기준을 적용하는 방식이다. 상태 이름(`unstable`)까지 같아진다. 비용은 창 수의 제곱으로 늘어(최대 K(K+1)/2 창 분량) 창당 시간 상한도 그만큼 커진다. 어느 방식을 기본으로 둘지는 design이 비용 측정(OP-1 기준선의 창당 시간)으로 정한다(G-13).

### N3.4 PDK 기술자(오라클 전용 파일, 엔진 선언 참조)

**위치(D-9 권고 (가))**: 엔진 선언 파일에 절을 더하지 않는다. 엔진 로더가 모르는 키를 거부하고 선언 sha256이 엔진 지문·9회로 기준선으로 흐르기 때문이다(F-13). 대신 오라클 전용 기술자 파일을 따로 두고, 그 파일이 엔진 선언 파일을 **경로 + sha256**으로 참조한다. 원본 PDK 파일(모델 카드, mismatch 파일, include 파일 등)의 경로·sha256은 **파일마다 정본 한 곳**이다(v0.5, 사용자 결정 O-3 = design DV-1 (가)): 엔진 선언 `sources`에 있는 파일은 엔진 선언이 정본이고 기술자는 source 키로만 가리킨다. 엔진 선언에 없는 파일(사례: 오라클이 include해야 하는 pmos `lod.spice`)만 기술자 `extra_sources`(경로·sha256)에 둔다. 같은 파일(같은 sha256 또는 같은 경로)이 두 곳에 나오면 기술자 로더가 거부한다(`descriptor_source_duplicated`). 기술자는 sha256이 맞을 때만 원본을 읽고, 다르면 `pdk_descriptor_stale`로 거부한다. **D-9와의 관계**: 엔진 선언에 없는 파일을 엔진 선언에 더하면 엔진 지문·9회로 기준선이 바뀌므로(D-9 위반) 그렇게 하지 않고, 대신 정본을 파일 단위로 나눈다. 나중에 엔진 선언이 그 파일을 갖게 되면 같은 변경에서 `extra_sources`에서 지운다(중복 거부 규칙이 강제한다). **이 계획은 엔진 선언 파일과 엔진 로더를 바꾸지 않는다.** 이관 초안 §2의 '엔진 PDK 선언 파일에 오라클 절' 안은 이 이유로 바꿨다(history H3).

**엔진 선언이 바뀔 때**(오케스트레이터 기본안): 기술자는 엔진 선언 sha256을 고정하므로 엔진 선언이 바뀌면 오라클은 `pdk_descriptor_stale`로 멈춘다. 그래서 **엔진 선언을 바꾸는 card가 같은 변경에서 기술자의 참조 sha256을 갱신**한다(기계적 갱신, 기술자의 다른 값은 그대로). 갱신 뒤 기존 능력 기록은 기술자 지문이 바뀌어 무효가 되고, 검증자가 다시 만든다. 그 사이 MC·온도 판정은 막히고 공칭 판정은 자동 대조만 통과하면 계속된다(X-13).

* **결정적 섭동 = 진단 도구**(O-1 (5)): 소자·변수마다 주어진 불일치 값을 넣는 결정적 섭동은 판정·게이트·능력 기록에 쓰지 않는다. 진단 도구는 어댑터 능력(소자별 변수 지정)이 있을 때만 돌고, 결과는 진단 보고에만 실린다. **배선**(만들면 배선, OP-5):
  * (i) **진입점**: `oracle_run`의 진단 입력 -- 주어진 섭동 벡터(소자 × 변수 값)를 넣어 op와 입력 환산 offset을 계산한다. 코어 MC 수학(V_os 식, DC servo, 차동 이득 부호)을 그대로 지난다.
  * (ii) **검증자 동일성 확인**(N4): 기준선 MC 표본을 같은 시드·같은 RNG로 재현해 그 값을 진단 경로로 넣고, 코어 MC 수학이 재작성 전후 비트 동일인지 판정한다. 네이티브 MC로 바뀌어 표본열이 달라져도 MC 수학 자체의 동일성은 이렇게 보인다(X-17 완화). 이것은 검증 절차이지 게이트가 아니라 O-1 (5)와 충돌하지 않는다.
  * (iii) **TR-7**: 엔진 σ_in과 오라클 MC σ_in이 맞지 않을 때 원인(어느 소자·변수·기하 환산)을 같은 진단 경로로 가른다.
| 코너 판정(향후) | 위 + 코너별 자동 대조 | design에서 정함 |

* **모델 묶음 비교 규칙**(N-a 반영): 두 쪽의 모양이 다르다.
  * LUT 쪽: 슬라이스 meta `model_files_sha256`은 슬라이스마다 '`pdk_root` 기준 상대 경로 → sha256' 표이고, 기록이 없으면 빈 표다(`E/lut/provenance.py:11-13, :51, :61`).
  * 오라클 쪽: kind마다 넷리스트 include를 재귀로 따라간 파일 묶음(절대 경로 → sha256)이다. 래퍼·코너 파일이 더 있을 수 있다.
  * 규칙(kind별, sha256 값 집합으로 비교, 경로는 비교하지 않음): (i) 오라클이 그 kind에 쓴 LUT 슬라이스들의 기록 sha256 집합 ⊆ 그 kind 오라클 묶음 sha256 집합 (ii) 오라클이 호출하는 모델(기술자의 모델 호출 이름)을 정의한 파일의 sha256 ∈ 그 LUT 기록 집합. 둘 중 하나라도 어기면 `model_bundle_mismatch`.
  * LUT 기록이 빈 표이면 비교할 수 없으므로 거부한다(`lut_model_provenance_missing`). 모델 파일 기록이 없는 옛 LUT를 쓰는 실행은 공칭 판정도 막힌다(X-14).

* **배선**(만들면 배선): MC 게이트는 OP-6에서 `oracle_offset_mc` 진입 경로에 바로 배선한다. 온도 게이트는 OP-5가 만든 '해석 요청 조건 = 온도' 경로(LUT `temp_c`와 다른 온도나 여러 온도를 요청하는 모든 실행)에 OP-6에서 배선한다. 그래서 TR-TL이 생기기 전에도 `oracle_run`에서 온도를 요청하면 게이트가 실제로 거부·허용한다. 범위 판정 규칙 자체는 offset-trim 소유다.

* **공정 무관 증거**: 같은 확인 코드가 두 기술자에서 돈다. (i) sky130 기술자(첫 사례) (ii) 손 모델 픽스처 기술자(시뮬레이터 내장 단순 모델 + 선언 불일치 변수, test 작성자가 독립으로 쓴다). 깨진 변형은 둘 다에서 거부된다. 실제 두 번째 PDK는 완료 조건이 아니다(D-8, X-1).

## N4. 동일성 판정 방법(ngspice 어댑터 대 기준선)

1. **기준선**(card OP-1): 이 기능 코드 변경 전 base에서 검증자가 오라클을 순차로 돌려 출력 JSON·Markdown을 기록한다. 입력 묶음 = `O/tests/fixtures`, `O/smoke/`의 oracle_input(한 회로, free/forced, sizing/layout), test가 쓰는 손 회로(`conftest.independent_cs/fb`, `u6_toy5t.py`), C10 fixture(지속 진동, 이완 진동, rhp 변형, 안정 회로), noise·offset_mc·swing 자체 점검 회로(`smoke/u6_selfchecks.py`). 정확한 목록과 실행 시간 예산은 OP-1에서 고정한다.
2. **비교 칸**:
   * 이산 칸(판정, `status`, 사유 코드, N·P·Z, `windows_run`, `early_stop` 유무, 제약 PASS/FAIL, 표본 수): 정확 일치.
   * 연속 칸(노드 전압, op 값, dB·위상, 주파수, 잡음, σ_in, 스윙 경계): 비트 동일이 목표다. 다르면 그 칸의 해 정확도 분해능(reltol·|x| + 해당 절대 허용오차, 입력 `testbench.options` 또는 어댑터 선언 기본값) 안이어야 하고 차를 기록한다. 분해능을 넘으면 실패다.
   * **MC 칸**(v0.4, O-1): 오라클 MC가 직접 섭동에서 네이티브 MC로 바뀌므로 표본열이 같지 않다. MC 칸(`sigma_in_mV`, `mean_in_mV` 등)은 동일성 판정에서 빼고, 기준선 값과 새 값의 차와 각 표준오차를 기록만 한다. MC 크기의 판정은 TR-7 §17-1 비교가 맡는다(X-17). MC 이산 칸(`status`, 사유)은 정확 일치 대상이다. **대신 코어 MC 수학은 비트 동일로 판정한다**: 기준선 MC 표본을 같은 시드·같은 RNG로 재현해 진단 경로(N3.5 '결정적 섭동 = 진단 도구' (ii))로 넣고, 표본별 V_os·σ_in이 기준선과 비트 동일인지 검증자가 판정한다.
   * 제외 칸: 실행 시간, 경로, 날짜, 새로 생긴 지문 칸(어댑터·기술자·능력 기록 id).
2a. **입력 변환**: 기준선은 옛 형식 입력으로, 비교 실행은 새 형식 입력(D-5)으로 돈다. 옛 입력 → 새 입력 변환은 **기계적 변환 스크립트**로 하고, 그 스크립트는 검증자가 쓰고 소유한다(코드 작성자의 변환 코드를 쓰지 않는다). 변환 규칙은 OP-0 design이 필드 대응표로 정하고, 변환 결과 파일과 sha256을 기준선 기록에 함께 둔다.
3. **넷리스트 텍스트 대조**(보조 증거): 어댑터가 쓴 넷리스트와 기준선 넷리스트를 정규화(원소 순서·이름 접두사)해 비교하고 차이를 기록한다. 판정은 2번이 한다.
4. 판정은 검증자가 한다(NFR-P5). 다른 결과가 나오면 멈추고 보고한다(기준 약화 금지).

### N5.2 다른 계획과의 순서·충돌

* **offset-trim**: TR-7(§17-1부터 MC 사용)과 TR-TL(보정 루프)은 OP-6이 sky130 능력 기록을 만든 뒤에 판정으로 센다(offset-trim v0.5.2 N3.9 순서 의존). 거꾸로 OP-6은 offset-trim G-15가 닫혀야 착수한다(PC-10). 온도 계층의 '합격'은 offset-trim G-14가 닫힐 때까지 나오지 않는다(그 계획에서 G-14 전 범위 판정은 '판정 불능', X-4). G-14는 사용자 결정 T-35로 네이티브 MC 표본 안에서 정해졌으므로 PC-11은 필요 없다. trim용 오라클 확장(코드 스윕·표본별 최적 코드, 레인 P)은 **OP-5 뒤 새 코어 위에서** 만든다(옛 구조에 만들고 다시 쓰지 않는다).
* **XRUN-F1·offset-strategy**: 이 계획의 OP-1~OP-6·OP-8은 `tools/spice_oracle/`·`assets/` 생성기·기술자 파일만 고친다. XRUN-F1(엔진 search·pipeline)과 offset-strategy(OS 카드: pipeline·authoring)와 파일이 겹치지 않는다. 엔진 파일을 고치는 것은 OP-7(D-4 승인 시, `E/lut/_helpers_bins.py`와 호출부, bin 규칙 선언을 읽는 경로)뿐이고, 9회로 비트 동일 기준선을 흔들지 않으려 XRUN-F1 card C 뒤에 둔다. OP-2는 오라클 전용 기술자 파일을 새로 만들 뿐 엔진 선언 파일·로더를 바꾸지 않으므로(D-9) 엔진 지문(`decl_sha256`)과 9회로 기준선에 닿지 않는다.
* **지연 추정**(X-4. **가정이고 측정이 아니다**): TR-7·TR-TL의 오라클 판정이 기다리는 것은 OP-0~OP-6, card 7개(문서 1, 검증자 1, 구현 5)와 상위 문서 개정(N3.7) 승인이다. 근거로 쓸 수 있는 과거 실측 하나: NFR-4 card 2는 design 보완 첫 커밋(2026-10-15 19:17)부터 병합(2026-10-16 12:15)까지 약 17시간이었고, 그 안에 판정 재작업이 한 번 있었다(master `git log`). 이 card들은 오라클 모듈 재작성이라 그보다 클 수 있고, ngspice 순차 실행(N9)이 시간을 더한다. 그래서 구현 card 하나에 하루에서 수일, 계획 승인 뒤 OP-6 병합까지 대략 1주~1개월로 넓게 잡는다. 실제 지연은 OP-6 병합 시점과 TR-7 착수 가능 시점(TR-6 병합)의 차로 잰다.
* **S-4 순서**(NFR-4 card 2 → XRUN-F1 A → B → C → 실행 계획 → TR-1)와 병렬로 레인 P에서 진행한다. 메모리 위험 때문에 ngspice 실행은 엔진 실행과 겹치지 않게 순차로 잡는다(N9).

### N5.3 완료 조건(기능 전체, 측정 가능)

1. **코어 무방언·무PDK**(측정 주체 = 검증자):
   * 대상 = 코어 모듈 집합 `O/core/` 아래 모든 `.py`(N0.1). **`O/core/` 안에는 `.py` 외 파일(JSON·템플릿·텍스트 데이터)을 두지 않는다.** 코어가 쓰는 데이터 파일은 어댑터나 기술자 쪽에 둔다. 검사는 `O/core/` 아래 `.py`가 아닌 파일 수 0(`__pycache__` 제외)을 함께 본다. 코어가 `O/core/` 밖 파일을 여는 경로는 입력·기술자·결과 파일뿐이다(design에서 목록화).
   * 방언 토큰 목록은 **검증자가 소유**하고(OP-1), 코어 어휘와 겹치지 않도록 **문법 형태**로 정의한다. 해석 이름 단독(`op`, `ac`, `noise`, `tran`, `pz`, `temp`)은 코어 어휘라 넣지 않는다. 넣는 것은 방언의 문법 형태다. 예: 점 지시문(`.pz`, `.control`, `.endc`, `.include`, `.lib`, `.option`, `.temp`, `.save`, `.nodeset`, `.ic`), 내부 벡터 틀(`@m.`, `[acmag]`), 스크립트 명령 형태(`alter `, `alterparam`, `wrdata`, `setplot`, `stop when`, `let `), 실행 인자 형태(`-b`).
   * **검사 방식**(Python 코드와 겹침 방지): 토큰은 코드 전체 텍스트가 아니라 **AST의 문자열 리터럴 내용**에만 적용하고, 경계를 둔 정규식으로 쓴다. 점 지시문과 스크립트 명령은 문자열의 머리 또는 줄 머리(공백 허용) 뒤에 올 때만 적중한다(예: `(^|\n)\s*\.(option|temp|include|lib|control|endc|save|nodeset|ic|pz)\b`, `(^|\n)\s*(alter|alterparam|wrdata|setplot|let|stop\s+when)\b`). `@m\.`·`\[acmag\]`은 리터럴 안 어디서나, `-b`는 리터럴 전체가 `-b`일 때만 적중한다. 그래서 Python의 메서드 호출 `.option`·변수 `temp`·주석의 'let'·연산 `-b`는 잡지 않는다. 주석과 docstring은 출처 인용이 허용되므로 검사에서 뺀다(docstring = 모듈·함수 첫 문자열 리터럴).
   * 검증자는 이 목록이 기준선 ngspice 넷리스트와 지금 오라클 코드의 문자열 리터럴에서 실제로 적중함을 먼저 보인다(게이트가 실제로 잡는다는 증거).
   * PDK 이름 = 저장소의 모든 기술자·엔진 선언 파일의 `pdk` 값과 모델 이름 패턴.
   * import 금지 목록 = 어댑터 패키지(`O/adapters/` 아래 모든 모듈)와 `subprocess`. AST import 검사로 0.
   * 결과: 위 셋 모두 0.
2. **stub 통과**: 코어 test가 stub 어댑터로 통과한다. stub은 조기 종결 능력을 선언하지 않아 D-1 전체 창 경로를 지난다. stub이 지나지 못하는 해석은 G-10 목록대로 'stub 실행' 또는 '능력 없음 거부 test'로 나눠 덮는다.
3. **ngspice 동일성**: N4 판정 통과(검증자 기록).
4. **능력 확인이 실제로 거부함**: PC-1~PC-3·PC-5~PC-8·PC-10마다 깨진 변형에서 거부(PC-3은 불일치가 꺼진 채 도는 선언·전역 공유 MC·끄기 안 되는 선언·전역 공정 변동이 함께 켜진 선언을 거부), 결정적 섭동 진단 도구가 게이트·능력 기록에 쓰이지 않음(호출 경로 증거), 유효 기록 없는 조합에서 MC 판정·온도 요청 거부(`oracle_capability_unverified`), 지문 하나 바꾼 기록 거부(`..._stale`), 모델 묶음 sha256 불일치 공칭 실행 거부(`model_bundle_mismatch`)를 test로 보인다. 같은 확인 코드가 sky130 기술자와 손 모델 기술자 둘에서 돈다.
5. **텍스트 단언 test 이전**: 코어 test 디렉터리에서 방언 텍스트 단언 0. 손 넷리스트 독립 기준(F-15)은 ngspice 어댑터 검증 test로 옮겨 그 어댑터의 기준이 된다. 나머지 텍스트 단언 test는 보존하지 않고 IR 단언·어댑터 단위 test로 새로 쓴다(test는 다시 써도 된다는 사용자 방침).
6. **삭제**: N3.6 삭제 목록의 이름 grep 0.
7. **배선**: 새 코어·어댑터·기술자 읽기·능력 확인 함수가 `oracle_run`과 측정 진입점에서 호출된다(호출 경로 증거). 결정적 섭동 진단 도구는 `oracle_run` 진단 입력에서 호출되고, 검증자 MC 수학 동일성 확인(N4)에서 실제로 쓰인다(그 판정 기록이 증거).
