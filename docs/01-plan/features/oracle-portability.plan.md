# oracle-portability Planning Document

> **Summary**: SPICE 오라클(`skills/analog-gmid-design/tools/spice_oracle/`)을 **시뮬레이터 무관·공정(PDK) 무관**으로 바꾼다. 구조는 세 층이다.
> 1. **오라클 코어**: 회로 IR, 측정 정의, 판정·비교 수학. 시뮬레이터와 PDK를 모른다.
> 2. **시뮬레이터 어댑터**: IR을 방언 넷리스트로 쓰고, 실행하고, 결과를 읽어 정규화한다. 자기 능력을 선언한다.
> 3. **PDK 기술자**: 오라클 전용 선언 파일이다. 엔진 `gmid_pdk_decl/1` 선언 파일을 경로·sha256으로 참조하고(엔진 파일·로더는 바꾸지 않음, D-9), 모델 호출 형식, include, 코너, 온도, MC 불일치 켜는 법, 확산 규칙, op 파라미터 이름, bin 경계 규칙을 담는다.
>
> 그리고 **공정 무관 오라클 능력 확인**(T-31)을 이 계획이 소유한다. 어떤 (PDK, 시뮬레이터) 조합에서 MC 불일치·온도 의존이 실제로 동작하는지 재는 절차, 기록 형식, fail-closed 규칙이다. offset-trim 계획(v0.5 N3.9)은 이것을 의존으로만 쓴다.
>
> 첫 어댑터는 ngspice, 첫 PDK는 sky130이다. 둘 다 **사례일 뿐**이고 규칙에는 이름을 넣지 않는다.

(로그를 옛 함수에 넣는 입력 경계 자체는 있다: 실행 캐시(`O/oracle_simulate.py:86-98` 키, `:104-121` `done` 슬롯이 있으면 ngspice를 돌리지 않고 저장된 로그를 돌려줌)와 모듈 전역 이름 `run_ngspice`의 교체(`O/oracle_offset_mc.py:38` `from oracle_simulate import ... run_ngspice`). 이 경계는 OP-1a의 선택 대조에 쓴다.) **그 재계산이 옛 코드와 같음의 검증**: 먼저 그 표본별 값으로 다시 낸 σ_in·mean_in이 기준선 출력의 `sigma_in_mV`·`mean_in_mV`와 비트 동일함을 보인다. 다르면 그 값을 기준선으로 쓰지 않고 멈추고 보고한다. 재계산값과 스크립트는 OP-1a가 보관한다 |

## N1. 목적·범위·요구

### N1.1 목적

사용자 취지(2026-10-16): gm/ID의 장점은 **작은 노력으로 SPICE와 작은 오차로 빠르게 설계**하는 것이고, 이것이 이번 개발의 가장 큰 이유다. 그 '작은 오차'를 재는 장치가 SPICE 오라클이다(상위 DEC-72 모델 오차, N3.8 `verified_by`). 오라클이 한 시뮬레이터·한 PDK에 묶여 있으면 다른 fab에서는 엔진 결과를 판정할 수 없다(T-31 "다른 fab에서도 사용할 수 있으니까").

이 기능의 목표는 둘이다.
1. 오라클 판정 로직이 시뮬레이터·PDK를 모르게 한다. 새 시뮬레이터는 어댑터 하나, 새 PDK는 기술자 파일 하나로 붙는다(T-33).
2. 어떤 (PDK, 시뮬레이터) 조합에서든 MC 불일치·온도 의존이 실제로 동작하는지 확인하는 절차를 두고, 확인되지 않은 조합에서는 그 판정을 거부한다(T-31).

### N3.1 3층 구조와 경계

```
오라클 코어 (시뮬레이터·PDK 모름)
  입력 검증 · 회로 IR 생성(본 회로 + 파생 테스트벤치) · 해석 요청 · 판정·비교(oracle_compare)
  · 안정성 수학(Nyquist, 창 판정, 조기 종결 규칙, RHP 집계, tran 계획) · 잡음 밀도·적분 · MC 표본 설계·입력 환산
  · 스윙 경계 탐색 · C15 topology 대조(IR 기준) · 능력 확인 절차의 벤치 IR과 판정
        │ IR + 해석 요청[]                ▲ 정규화 결과
        ▼                                 │
시뮬레이터 어댑터 (사례: ngspice)
  방언 쓰기 · 실행 · 결과 읽기 · 내부 벡터 이름 대응 · 극성 정규화 · 오류 분류 · 캐시 키 · 능력 선언·보정값
        ▲ 모델 호출 형식, include, 코너·온도 지정, MC 방법, op 파라미터 이름 집합

```

**경계 규칙**:
1. 코어(`O/core/`)는 어댑터 패키지(`O/adapters/` 아래 모든 모듈)와 `subprocess`를 import하지 않는다. 진입점이 선택된 어댑터를 주입한다. 프로세스 실행은 어댑터만 한다.
2. 어댑터는 판정하지 않는다. 판정에 필요한 분해능(해 정확도)은 값으로 넘긴다.
3. 기술자는 데이터다. 기술자에 코드(식 평가 외)를 넣지 않는다. 식은 `gmid_pdk_decl/1`의 '원본 파일 값으로 계산하는 식' 형식을 따른다.
4. 시뮬레이터 결함 회피(예: pz 거짓 RHP 극)는 두 부분으로 나눈다. **코어**는 '극점 결과는 독립 증거(개루프 과도)로 확인될 때만 판정에 쓴다'는 일반 규칙을 갖고, **어댑터**는 pz 능력과 그 신뢰 범위를 선언한다. 어느 쪽이 회로 이론 규칙이고 어느 쪽이 회피책인지 design이 항목마다 적는다(G-3).

### N3.2 회로 IR·해석 요청·정규화 결과

* **IR이 만드는 것**: 본 회로(free/forced/iso), β 루프, 개루프 pz, noise, MC 래퍼, 스윙 servo 이동, ratio·rout 여기, C10 과도 테스트벤치. 지금 텍스트 재작성으로 하던 변형(F-4)은 전부 IR 변환으로 한다.
* **이름 규칙**: 원소 이름 접두사(지금 `X`, `Rp_`, `Vsrc_` 등)는 방언 규약이라 어댑터가 정한다. IR은 원소 종류를 필드로 갖는다. 대소문자 충돌 검사(지금 넷 이름 대소문자 무시 전제)는 어댑터 능력(`case_insensitive_names`)으로 선언하고, 코어는 선언에 따라 충돌을 거부한다.
* **결과 키**: 소자 값은 IR 소자 이름, 넷 값은 IR 넷 이름으로 돌아온다. 잡음 기여도 IR 소자 이름 기준이다(F-8의 내부 경로 해석은 어댑터 + 기술자 모델 호출 형식이 한다).
* **오류 분류**: 어댑터가 로그를 공통 코드로 바꾼다(예: 수렴 실패, 특이 행렬, 시간 걸음 실패, 시간 초과, 모델 없음). 코드 집합은 G-4.
* **형식 정본**: IR·요청·결과의 스키마는 design이 정한다(G-1, G-2).

### N3.3 어댑터 능력 선언과 C10 조기 종결(D-1)

* 어댑터는 능력 목록을 선언한다. 후보(ngspice 기능에서 거꾸로 뽑은 것이라 확정 목록은 G-3): 창 단위 조기 종결(실행 중 조건부 정지·재개), pz, 네이티브 MC 표본 실행(기술자가 선언한 불일치 켜는 법으로, 난수는 시뮬레이터 RNG(N0.1), 표본 시드·표본 정체 보존·소자별 독립 여부 선언, 지원하는 켜는 법 종류 선언), AC 여기 전환, 온도 지정, op 스윕, 잡음 기여 분해, 극성 정규화가 정의된 모델 계열.
* 보정값: 기본 허용오차(지금 `_NGSPICE_DEFAULT_TOL`, 출처는 그 시뮬레이터 문서 기본값), 데이터 자릿수(지금 `WRDATA_NUMDGT`), 창당 실행 시간 상한(지금 `oracle_config.json`). 측정 조건·코퍼스·출처를 함께 선언한다. 상한 보정값이 없는 어댑터에서는 C10 과도가 사용자 `--timeout-s` 없이는 거부한다(오케스트레이터 기본안, `adapter_calibration_missing`).
* **D-1 권고**: C10 판정 규칙(f_crit, n_pp, tmax, 창 판정 g↑·g↓, 조기 unstable, 한계 사이클)은 코어가 정의한다. 시뮬레이터 안 조기 종결은 어댑터 능력이다. 능력이 있으면 어댑터가 코어 규칙을 방언으로 옮겨 시뮬레이터 안에서 멈추고, 코어는 지금처럼 파일로 같은 기준을 다시 검증한다. 능력이 없으면 전체 창을 실행하고 코어가 같은 기준을 사후에 적용한다.
  * '결과 동일'의 범위: 전체 창 실행이 끝까지 가면 판정 상태(`unstable`·`stable` 등)가 같다. 다만 조기 종결은 원래 GHz 진동 회로가 끝나지 않는 문제(계약 §0)를 막으려고 생겼다. 능력이 없는 어댑터에서 그런 회로는 시간 상한에 걸려 `failed`가 될 수 있다. 이때도 PASS 불가라는 판정 결론은 같지만 상태 이름은 다르다(X-2).
  * **검토할 대안(재실행 방식)**: 능력이 없는 어댑터에서도 창 j를 끝낼 때마다 tstop = t_end + j·W로 늘려 처음부터 다시 실행하고, 코어가 매번 조기 unstable 기준을 적용하는 방식이다. 상태 이름(`unstable`)까지 같아진다. 비용은 창 수의 제곱으로 늘어(최대 K(K+1)/2 창 분량) 창당 시간 상한도 그만큼 커진다. 어느 방식을 기본으로 둘지는 design이 비용 측정(OP-1 기준선의 창당 시간)으로 정한다(G-13).

### N3.4 PDK 기술자(오라클 전용 파일, 엔진 선언 참조)

**위치(D-9 권고 (가))**: 엔진 선언 파일에 절을 더하지 않는다. 엔진 로더가 모르는 키를 거부하고 선언 sha256이 엔진 지문·9회로 기준선으로 흐르기 때문이다(F-13). 대신 오라클 전용 기술자 파일을 따로 두고, 그 파일이 엔진 선언 파일을 **경로 + sha256**으로 참조한다. 원본 PDK 파일(모델 카드, mismatch 파일, include 파일 등)의 경로·sha256은 **파일마다 정본 한 곳**이다(v0.5, 사용자 결정 O-3 = design DV-1 (가)): 엔진 선언 `sources`에 있는 파일은 엔진 선언이 정본이고 기술자는 source 키로만 가리킨다. 엔진 선언에 없는 파일(사례: 오라클이 include해야 하는 pmos `lod.spice`)만 기술자 `extra_sources`(경로·sha256)에 둔다. 같은 파일(같은 sha256 또는 같은 경로)이 두 곳에 나오면 기술자 로더가 거부한다(`descriptor_source_duplicated`. v0.6.7: '같은 sha256'의 판정은 아래 'sha256 정의' 규칙 (iii)). 기술자는 sha256이 맞을 때만 원본을 읽고, 다르면 `pdk_descriptor_stale`로 거부한다. **D-9와의 관계**: 엔진 선언에 없는 파일을 엔진 선언에 더하면 엔진 지문·9회로 기준선이 바뀌므로(D-9 위반) 그렇게 하지 않고, 대신 정본을 파일 단위로 나눈다. 나중에 엔진 선언이 그 파일을 갖게 되면 같은 변경에서 `extra_sources`에서 지운다(중복 거부 규칙이 강제한다). **이 계획은 엔진 선언 파일과 엔진 로더를 바꾸지 않는다.** 이관 초안 §2의 '엔진 PDK 선언 파일에 오라클 절' 안은 이 이유로 바꿨다(history H3).

**엔진 선언이 바뀔 때**(오케스트레이터 기본안): 기술자는 엔진 선언 sha256을 고정하므로 엔진 선언이 바뀌면 오라클은 `pdk_descriptor_stale`로 멈춘다. 그래서 **엔진 선언을 바꾸는 card가 같은 변경에서 기술자의 참조 sha256을 갱신**한다(기계적 갱신, 기술자의 다른 값은 그대로. v0.6.7: 갱신 값은 그 파일의 LF 정규화 sha256이고 엔진 `decl_sha256` 값을 옮겨 적지 않는다 -- 아래 'sha256 정의'). 갱신 뒤 기존 능력 기록은 기술자 지문이 바뀌어 무효가 되고, 검증자가 다시 만든다. 그 사이 MC·온도 판정은 막히고 공칭 판정은 자동 대조만 통과하면 계속된다(X-13).

**sha256 정의**(v0.6.7, 사용자 결정 O-13 (5) = J-15 (다), F-19). 기술자 참조 sha256이 체크아웃 줄 끝에 따라 달라지면 같은 저장소를 LF로 체크아웃한 기계에서 오라클이 `pdk_descriptor_stale`로 멈춘다. 그래서 정의를 둘로 나누고 비교 규칙을 정한다.

* **(i) 정본 = LF 정규화 sha256**(N0.1). 적용 대상 = **오라클 기술자가 새로 적는 참조 sha256 전부**: `engine_decl.sha256`, `lut_record_root.location_decl.sha256`, `extra_sources.<키>.sha256`, 그리고 `lut_file_roles`(검증자 옆 선언 참조, design §10.2)의 sha256. 넷째는 결정 원문 괄호 목록(`engine_decl`, `location_decl`, `extra_sources`)에 없지만 같은 종류(기술자가 가리키는 저장소 안 텍스트 파일이고, 이 계획이 새로 쓰는 값이라 옛 raw 기록이 없다)라 같은 정의를 쓴다(오케스트레이터 해석 -- 결정 취지 '기술자 참조 파일의 정본 sha256' 안). 이 칸들에는 raw 값을 받지 않는다: raw로만 맞으면 `pdk_descriptor_stale`로 거부한다(옛 기록이 아니므로 규칙 (ii)의 대상이 아니다. 오케스트레이터 해석, 기준 강화). **같은 정의를 쓰는 오라클 쪽 지문**(사용자 결정 O-14 (3), 2026-10-19 = 옛 OQ-5 기본안 확정): 기술자 파일 자체의 sha256(능력 기록·FR-P9 결과의 기술자 지문), 오라클 입력 `process.descriptor.sha256`(design §11.1), 능력 기록의 어댑터 코드 지문(N3.5 -- 파일마다 이 정의, `calibration.json`은 그대로 정규 JSON), 능력 기록의 확인 코드 지문 `check_code_fp`(design §12.4). 넷 모두 이 계획이 새로 만드는 값이라 옛 raw 기록이 없고 raw 값을 받지 않는다.
  * **정의 사본 셋**(design X-D5 '오라클 재구현 사본 유지'와 같은 처리): 같은 정규화 정의가 엔진(`E/core/pdk_decl.py:336-337`), 오라클 코어(기술자 로더·묶음 대조·지문 -- 코어 한 곳), X-13 test(엔진 suite, 엔진·오라클 코드를 import하지 않으므로 test 안에 한 줄로 씀) 세 곳에 있다. 오라클은 엔진을 import하지 않으므로(NFR-P3) 하나로 합치지 않고 사본을 유지한다. 정의(N0.1)를 바꾸는 변경은 같은 변경에서 세 사본과 그 test 기대값을 함께 고친다.
  * **무엇을 바꾸나 -- CRLF → LF만**: 정규화는 두 바이트 `\r\n`을 `\n`으로 바꾸는 것 하나다. 근거(P-1, 원인에 맞춘 최소 변환): 값이 기계마다 달라지는 원인은 git의 줄 끝 변환(`core.autocrlf`)이고, 그 변환이 바꾸는 것은 LF ↔ CRLF뿐이다. 홀로 있는 `\r`은 체크아웃이 만들거나 지우지 않으므로 파일 내용이고, 그것까지 바꾸면 실제로 다른 두 파일을 같다고 판정한다. 같은 정의가 엔진에 이미 있다(`newline: "lf"`, `E/core/CONTRACT.md:324`, 선례 `A/sky130_lut_rule_decl.json:10`). 정의를 하나로 두어야 같은 파일의 '정규화 값'이 오라클과 엔진에서 같다(둘째 정규화 변형을 만들지 않는다).
  * **BOM -- 바꾸지 않는다**: 줄 끝 변환은 BOM을 더하거나 지우지 않는다(이 저장소에는 `working-tree-encoding` 같은 인코딩 변환 설정도 없다 -- `.gitattributes` 없음, F-19). 그래서 BOM은 기계 설정이 아니라 파일 내용이고, BOM이 다르면 다른 파일로 거부된다. 엔진 `newline: "lf"`도 BOM을 건드리지 않는다.
  * **바이너리 -- 내용으로 판정하지 않는다**: 바이트 내용·이름·확장자로 '텍스트인가'를 추측하지 않는다(git의 '앞 N바이트에 NUL' 같은 판정은 새 상수가 되고, 역할을 이름·확장자로 정하지 않는다는 규칙(N3.5 '역할은 선언으로 정한다')과도 어긋난다). 위 적용 대상은 **참조 칸의 종류가 텍스트를 정한다**: 엔진 선언·위치 선언·옆 선언은 JSON, `extra_sources`는 시뮬레이터가 include하는 PDK 텍스트 원본이다. 바이너리 파일을 가리켜야 하는 참조 칸이 생기면 그 칸은 raw 정의를 **선언으로** 갖는다(스키마 개정 -- 계획 개정 대상, 조용한 예외 없음). 정규화는 바이트 연산이라 어떤 바이트에도 결정적이다. 잃는 것은 'CRLF/LF만 다른 두 파일'을 구별하는 능력뿐이고, 위 텍스트 참조 칸에서는 바로 그 차이를 같게 보는 것이 목적이다.
  * 새 상수 없음: 바꾸는 바이트열은 정의 자체(줄 끝 기호)이고 조정값이 아니다.
* **(ii) 옛 raw 기록값 = 같은 기계에서만, '기계 의존' 표시**. 대상 = 이 계획 밖에서 raw 정의로 적힌 기록이다: 엔진 선언 `sources.<키>.sha256` 가운데 `newline` 키가 없는 항목(지금 `A/sky130_pdk_decl.json` `sources` **9개 전부**. 그 가운데 지금 디스크가 CRLF라 raw ≠ 정규화인 것은 7개 -- 모델 카드 둘, mismatch slope 둘, `mim_cap_params`, `scale_option`, `poly_res_params`, F-19. 엔진 계약의 기록 `E/core/CONTRACT.md:418-425`), LUT meta `model_files_sha256`(N3.5 '모델 묶음 비교 규칙'), LUT meta `generator_sha256`(N3.5 '역할은 선언으로 정한다' 근거 (a) 생성기 판 찾기 -- 저장소 이력의 후보 판마다 그 판 바이트의 정규화 sha256, 아니면 그 판을 이 기계 줄 끝 설정으로 체크아웃한 바이트의 sha256과 대조하고, 뒤쪽으로만 맞으면 기계 의존 일치). 이 기록은 엔진 소유라 이 계획이 바꾸지 않는다(D-9, N1.2 '기존 공유 LUT 데이터 파일 수정 제외'). 대조: 기록값 = 그 파일의 LF 정규화 sha256이면 일치, 아니고 기록값 = raw sha256이면 **기계 의존 일치**(N0.1)로 받되 결과 JSON(FR-P9)과 능력 기록에 그 참조를 '기계 의존'으로 적는다, 둘 다 아니면 그 자리의 기존 오류(`pdk_descriptor_stale`, `model_bundle_mismatch`, 보조 입력 불일치)로 거부한다(fail-closed). `newline: "lf"`가 있는 엔진 원본 항목은 기록이 이미 정규화 값이라 첫 비교에서 맞는다. **결과**: 기계 의존 일치는 그 기록을 쓴 기계와 줄 끝이 같은 체크아웃에서만 성립하므로, LF 체크아웃에서는 그 엔진 원본·LUT 기록이 맞지 않아 거부된다 -- 엔진 기록을 고치는 card가 생길 때까지 오라클 전체의 '기계 무관'은 기술자 자기 칸에서만 성립한다(X-27, N3.7 'v0.6.7 상위 계획 개정 항목').
* **(iii) 정의가 다른 값을 서로 비교하지 않는다**(결정 (iv)). 두 기록이 같은 파일인지(중복 검사), 기술자 참조가 엔진 선언과 맞는지(X-13)는 **기록값끼리**가 아니라 **파일 바이트에서 다시 잰 값**으로 판정한다:
  * X-13 (a): 기술자 `engine_decl.sha256` = 엔진 선언 파일 바이트의 LF 정규화 sha256(test가 파일에서 직접 잰다). 엔진 `decl_sha256`(raw 정의, `E/core/pdk_decl.py:619`) 값과 견주지 않는다 -- 같은 파일이라도 CRLF 체크아웃에서 두 값은 다르다(F-19 `24f970d5…` 대 `5f32257b…`).
  * 중복(`descriptor_source_duplicated`, X-13 (b)): 경로 집합의 교집합 = ∅, 그리고 **엔진 선언 `sources`의 모든 파일**(기술자가 쓰지 않는 원본 포함 -- 사례 `mim_cap_params`·`poly_res_params`·`scale_option`)과 `extra_sources`의 모든 파일을 **파일 바이트에서 LF 정규화 sha256으로 다시 재어** 두 집합의 교집합 = ∅. 엔진 `sources` 기록값과 견주지 않는다: 기록이 raw인 엔진 원본은 LF 체크아웃 기계에서 같은 내용의 `extra_sources` 파일의 정규화·raw 어느 값과도 다르고, 기술자가 쓰지 않는 원본은 규칙 (ii)의 대조에도 걸리지 않으므로 기록값 비교는 중복을 놓친다(fail-open, v0.6.7 독립 검증 지적 1). 두 쪽 어느 파일이든 없으면 거부한다(대조 불가를 통과로 세지 않는다). 그래서 기술자가 쓰지 않는 엔진 원본(사례 `tech_lef`, `periphery_rules`)도 오라클을 돌리는 기계에 있어야 한다 -- 엔진 로더가 선언 원본 전부를 읽고 없으면 `pdk_source_missing`으로 거부하는 것과 같은 요구다(`E/core/pdk_decl.py:332-333`).
  * 기록 뿌리 교차 검사(`lut_record_root_mismatch`, design §10.2·§7.2 8단계 -- LUT 기록과 엔진 선언 `sources`에 같은 파일이 있으면 두 뿌리가 같은 PDK 트리를 가리키는지 본다): '같은 파일'을 LUT 기록 sha256과 엔진 `sources` 기록 sha256의 값 비교로 정하지 않는다. 또 짝을 '두 뿌리 아래 파일을 다시 잰 값이 같은가'로 고르지 않는다 -- 그러면 같은 값인 것만 짝이 되어 검사가 늘 통과하고, 다른 PDK 트리를 가리키는 뿌리를 거부하지 못한다(재검증 지적). 두 단계로 한다: **(1) 짝 고르기** = LUT 기록 항목(상대 경로, 기록값)마다, 기록값이 어떤 엔진 원본 파일(엔진 선언 경로의 파일)의 LF 정규화 sha256 또는 raw sha256과 같으면 (그 상대 경로, 그 엔진 원본)을 짝으로 둔다. 이것은 기록 하나를 파일 바이트에 대조하는 규칙 (ii)이고 정의가 다른 기록값끼리의 비교가 아니다. **(2) 짝마다 판정** = 기술자 `lut_record_root`로 푼 뿌리 아래 그 상대 경로 파일의 LF 정규화 sha256 == 그 엔진 원본 파일의 LF 정규화 sha256이어야 하고, 다르면 `lut_record_root_mismatch`, 그 상대 경로에 파일이 없으면 거부한다(대조 불가를 통과로 세지 않는다). 이 검사 함수와 test는 OP-3이 만든다(사용자 결정 O-14 (4) J-5 (가)). OP-3 test는 **다른 트리를 가리키는 뿌리 → `lut_record_root_mismatch`** 거부 변형과 뿌리 아래 짝 파일이 없는 변형의 거부를 먼저 보인다.
  * 엔진 선언 파일 하나가 엔진 쪽에서는 raw `decl_sha256`으로, 오라클 쪽에서는 정규화 값으로 적히는 것은 정의 차이이고 불일치가 아니다. 두 값을 같은 칸에 섞어 적거나 한쪽 값을 다른 쪽으로 옮겨 적지 않는다(X-26).

* **공정 무관 증거**: 같은 확인 코드가 두 기술자에서 돈다. (i) sky130 기술자(첫 사례) (ii) 손 모델 픽스처 기술자(시뮬레이터 내장 단순 모델 + 면적 의존이 있는 선언 불일치 변수, test 작성자가 독립으로 쓴다). **이 기술자는 OP-5 산출물인 정본 파일 하나이고**(완료 조건 4a의 기술자와 같은 파일), OP-6 능력 확인은 그것을 재사용한다(v0.6.1). 깨진 변형은 둘 다에서 거부된다. 실제 두 번째 PDK는 완료 조건이 아니다(D-8, X-1).

## N4. 동일성 판정 방법(ngspice 어댑터 대 기준선)

1. **기준선**(card OP-1): 이 기능 코드 변경 전 base에서 검증자가 오라클을 순차로 돌려 출력 JSON·Markdown을 기록한다. 입력 묶음 = `O/tests/fixtures`, `O/smoke/`의 oracle_input(한 회로, free/forced, sizing/layout), test가 쓰는 손 회로(`conftest.independent_cs/fb`, `u6_toy5t.py`), C10 fixture(지속 진동, 이완 진동, rhp 변형, 안정 회로), noise·offset_mc·swing 자체 점검 회로(`smoke/u6_selfchecks.py`. B-20(OP-3)으로 이 파일을 지운 뒤 OP-5의 N4 비교는 OP-1a에 보관한 입력을 쓴다). 정확한 목록과 실행 시간 예산은 OP-1에서 고정한다. **보관**(v0.6.3, 사용자 L-1 (2)·L-2 (9)): 기준선 원자료(넷리스트 1,158·입력 593, 약 177 MB, `wt/_scratch_op1/baseline`)는 저장소 밖에 두고, 판정에 쓰는 텍스트(약 15-19 MB)와 원자료 전체의 sha256 목록을 `.ai/verification/<OP-1 id>/baseline/`에 커밋한다(card OP-1a). 그래서 N4 동일성 판정이 옛 엔진(`legacy/`, gain-budget LT-1에서 삭제)과 저장소 밖 경로 없이 된다.
2. **비교 칸**:
   * 이산 칸(판정, `status`, 사유 코드, N·P·Z, `windows_run`, `early_stop` 유무, 제약 PASS/FAIL, 표본 수): 정확 일치.
   * 연속 칸(노드 전압, op 값, dB·위상, 주파수, 잡음, σ_in, 스윙 경계): 비트 동일이 목표다. 다르면 그 칸의 해 정확도 분해능(reltol·|x| + 해당 절대 허용오차, 입력 `simulator.options` 또는 출처 있는 어댑터 보정값) 안이어야 하고 차를 기록한다. 분해능을 넘으면 실패다.
   * **MC 칸**(v0.4, O-1. v0.6.3 O-8로 판정 둘로 나눔): 오라클 MC가 직접 섭동에서 네이티브 MC로 바뀌므로 표본열이 같지 않다. MC 칸(`sigma_in_mV`, `mean_in_mV` 등)은 동일성 판정에서 빼고, 기준선 값과 새 값의 차와 각 표준오차를 기록만 한다. MC 크기의 판정은 TR-7 §17-1 비교가 맡는다(X-17). MC 이산 칸(`status`, 사유)은 정확 일치 대상이다. **대신 MC 수학은 검증자가 둘로 판정한다**(N3.5 '결정적 섭동 = 진단 도구' (ii)): (가-1) 기준선 로그의 표본별 op 값을 새 코어 MC 수학에 넣은 표본별 V_os·σ_in·mean_in이 기준선과 비트 동일 (가-2) 기준선 표본을 같은 시드·같은 RNG로 재현해 진단 경로로 끝까지 낸 표본별 V_os는 비트 동일이 목표이고, 다르면 위 연속 칸 분해능 안 + 차 기록(넘으면 실패). σ_in·mean_in은 (가-2)로 판정하지 않는다(X-19, 이 부분은 오케스트레이터 해석 -- OQ-4 승인됨(L-3)). (가-1)·(가-2)가 비교하는 기준선 표본별 V_os는 N0.1 '기준선'이 정의한 검증자 재계산값이다(v0.6.5, O-9 DV-5).
   * 제외 칸: 실행 시간, 경로, 날짜, 새로 생긴 지문 칸(어댑터·기술자·능력 기록 id).
2a. **입력 변환**: 기준선은 옛 형식 입력으로, 비교 실행은 새 형식 입력(D-5)으로 돈다. 옛 입력 → 새 입력 변환은 **기계적 변환 스크립트**로 하고, 그 스크립트는 검증자가 쓰고 소유한다(코드 작성자의 변환 코드를 쓰지 않는다). 변환 규칙은 OP-0 design이 필드 대응표로 정하고, 변환 결과 파일과 sha256을 기준선 기록에 함께 둔다. (v0.6.3) 변환 결과는 판정 기록 안에만 두고 저장소의 배포 산출물(`O/smoke/` 입력 등)을 만들거나 바꾸지 않는다 -- 검증자 스크립트가 배포 산출물을 만들면 작성자≠검증자(NFR-P5)가 무너진다. 저장소에 새 형식 smoke 입력이 필요해지면 code 역할 card로 만든다(X-5). **예외**(v0.6.3.1, OP-7 선례): **측정 결과를 담은 옆 선언**(OP-7 bin 규칙 옆 선언, OP-3 (c) LUT 기록 역할 옆 선언)은 검증자가 쓰고 저장소에 둔다. 그 값의 근거가 검증자 측정이라 코드 작성자가 쓰면 자기 측정을 자기가 판정하게 되기 때문이다. 경계: 옆 선언은 측정값과 그 근거만 담는 데이터이고, 오라클 입력·넷리스트·코드처럼 피검 경로가 만들어 내야 하는 산출물이 아니다.
3. **넷리스트 텍스트 대조**(보조 증거): 어댑터가 쓴 넷리스트와 기준선 넷리스트를 정규화(원소 순서·이름 접두사)해 비교하고 차이를 기록한다. 판정은 2번이 한다.
4. 판정은 검증자가 한다(NFR-P5). 다른 결과가 나오면 멈추고 보고한다(기준 약화 금지).

   * 방언 토큰 목록은 **검증자가 소유**하고(OP-1), 코어 어휘와 겹치지 않도록 **문법 형태**로 정의한다. 해석 이름 단독(`op`, `ac`, `noise`, `tran`, `pz`, `temp`)은 코어 어휘라 넣지 않는다. 넣는 것은 방언의 문법 형태다. 예: 점 지시문(`.pz`, `.control`, `.endc`, `.include`, `.lib`, `.option`, `.temp`, `.save`, `.nodeset`, `.ic`), 내부 벡터 틀(`@m.`, `[acmag]`), 스크립트 명령 형태(`alter `, `alterparam`, `wrdata`, `setplot`, `stop when`, `let `), 실행 인자 형태(`-b`).
   * **검사 방식**(Python 코드와 겹침 방지): 토큰은 코드 전체 텍스트가 아니라 **AST의 문자열 리터럴 내용**에만 적용하고, 경계를 둔 정규식으로 쓴다. 점 지시문과 스크립트 명령은 문자열의 머리 또는 줄 머리(공백 허용) 뒤에 올 때만 적중한다(예: `(^|\n)\s*\.(option|temp|include|lib|control|endc|save|nodeset|ic|pz)\b`, `(^|\n)\s*(alter|alterparam|wrdata|setplot|let|stop\s+when)\b`). `@m\.`·`\[acmag\]`은 리터럴 안 어디서나, `-b`는 리터럴 전체가 `-b`일 때만 적중한다. 그래서 Python의 메서드 호출 `.option`·변수 `temp`·주석의 'let'·연산 `-b`는 잡지 않는다. 주석과 docstring은 출처 인용이 허용되므로 검사에서 뺀다(docstring = 모듈·함수 첫 문자열 리터럴).
   * 검증자는 이 목록이 기준선 ngspice 넷리스트와 지금 오라클 코드의 문자열 리터럴에서 실제로 적중함을 먼저 보인다(게이트가 실제로 잡는다는 증거). **적중 증거의 출처 단계**(v0.6.3, 오케스트레이터 기본안 -- 원래 취지와 다름 X-23, 사용자 결정 OQ-2 승인됨(L-3)): 옛 오라클이 쓰지 않던 방언 형태(사례: 분포·난수 함수 형태 -- 옛 오라클은 분포 함수를 쓰지 않아 OP-1 사전 점검에서 기준선 어디서도 적중하지 않았다, OP-0 design S-16)는 기준선으로 적중을 보일 수 없다. 그런 토큰은 그 형태를 처음 쓰는 card(사례: 네이티브 MC 켜는 법을 어댑터가 쓰는 OP-5)가 병합된 뒤 목록에 넣고, 적중 증거는 그 card의 **어댑터 산출 넷리스트**로 보인다. 그 전까지 검사는 그 토큰을 뺀 목록으로 돌고, 목록에 단계(기준선 증거 / 어느 card 산출물 증거)를 적는다. 적중을 보이지 못한 토큰을 목록에 넣은 채 '0'을 합격으로 세지 않는다.
   * PDK 이름 = 저장소의 모든 기술자·엔진 선언 파일의 `pdk` 값과 모델 이름 패턴.
   * import 금지 목록 = 어댑터 패키지(`O/adapters/` 아래 모든 모듈)와 `subprocess`. AST import 검사로 0.
