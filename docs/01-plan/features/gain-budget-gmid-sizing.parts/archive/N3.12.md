### N3.12 역할 분리 -- 폐기(2026-10-07, gate 끔)

> **폐기(2026-10-07, gate 끔, DEC-86)** -- 역할 분리 gate·hook·판정 기록·spec card 흐름을 껐다. 아래 N3.12.0~N3.12.6은 기록으로 남기고 적용하지 않는다. 남는 것: 코드 작성 주체와 test·기대값 작성 주체 분리(WP-13), 약화 보고·변경당 커밋 1·매 변경 뒤 전체 test(DEC-86, N6.3). 일반 test로 옮긴 판정은 N4.2·N4.3 머리 목록에 있다.

#### N3.12.0 위협 범위

역할 분리가 **막는 것**과 **막지 않고 드러나게 하는 것**을 가른다(2026-09-18 사용자 결정 C). 모든 주체(오케스트레이터, 세 역할)는 같은 OS 계정·같은 디스크에서 돈다 -- 그래서 로컬 게이트는 그 계정이 실행하는 코드가 **의도적으로** 부수는 것을 막을 수 없다(실측: 작업 저장소 git 설정 한 줄로 gate `pre-receive`를 건너뛰었고, gate 안에서 실행된 test 코드가 gate hook을 덮어썼다. 원자료 `review29_05_v2.md`).

| 구분 | 대상 | 장치 |
|---|---|---|
| **막는다**(게이트가 거부) | 이력에 실제로 있던 자기 은폐 패턴: 기준 약화(assert 삭제·완화, 리터럴 변경, 허용오차·격자 확대, skip/xfail), 코드와 기준의 동시 변경, 자기참조 기대값, 광범위 except로 삼키기, 역할 밖 편집(엔진 소스를 메인 세션이 쓰기 등), 판정 환경 조작(`conftest.py`·`pytest.ini` 등), 검사 끄기(`--no-verify`, `core.hooksPath`), 트레일러·역할 흉내, 흐름 밖 병합 | EL1~EL4, V1~V10(원자료 `agent7_self_concealment.md`) |
| **막지 않고 드러나게 한다** | 같은 계정 권한으로 게이트 자체를 부수는 의도적 행위: gate 저장소 파일·참조 직접 수정, 원격 설정 조작(`receivepack`·`url.*`), 파이썬 스크립트 등 hook이 보지 못하는 경로로 만든 커밋·쓰기 | 무결성 대조(gate hook·설정·master 참조를 승인된 값·기록과 대조, 세션 시작과 매 gate push 때), 판정 기록의 증거 재실행을 **격리된 임시 복제본**에서, 사용자가 보는 감사 로그. 감지되면 모든 게이트가 거부하고 사용자에게 알린다 |
| 범위 밖 | 다른 OS 계정·원격 서버 수준의 경계 | 필요해지면 계획 개정으로 올린다(원격 보호 브랜치 + 필수 CI 등) |

* **게이트는 push된 코드를 실행하지 않는다.** 증거 재실행(red 재현, equivalence 명령)은 auditor 단계에서 격리 복제본으로 하고, gate `pre-receive`는 커밋 구조·경로·트레일러·판정 기록·해시만 판정한다(실행하면 그 코드가 gate를 바꿀 수 있다).
* 승인 기록은 오케스트레이터가 쓴다(N3.12.5). 게이트는 승인 기록의 존재·형식·해시까지 증명하고 그것이 사용자의 실제 승인인지는 증명하지 못한다 -- 사용자가 커밋 이력으로 확인한다.

#### N3.12.2 쓰기 경로표

이 표가 쓰기 권한의 정본이고, hook과 게이트(EL1~EL4)는 이 표를 **직접 파싱**한다(사본을 두지 않는다 -- 파싱 규칙은 `05-role-separation` design). 한 행에 glob 하나다. glob은 저장소(worktree) 루트 기준 상대 경로이고 대소문자를 무시해 대조한다(Windows 파일 시스템과 같게 -- `Pytest.ini`도 `**/pytest.ini` 행에 맞는다). `*`는 한 경로 조각, `**`는 여러 조각, `<id>`는 그 worktree의 변경 id(브랜치 `role/<역할>/<id>`의 `<id>`)다. 한 경로가 쓰기 가능하려면 그 주체의 행 중 하나에 '경로 glob'으로 맞고 '제외 glob'에 맞지 않으며 '조건'을 만족해야 한다. 이 표의 파싱 값이 바뀌는 계획 개정은 판정 표 변경과 같이 승인 기록이 필요하다(N3.12.4 EL3·EL4).

조건 값: `없음` / `자기 변경 id`(`<id>`가 그 worktree의 변경 id와 같다) / `게이트 변경`(그 변경의 spec card가 게이트 변경이고 승인 기록이 있다) / `부트스트랩`(N3.12.6 ①~④ 한정 -- gate `master`에 부트스트랩 완료 표지(`tools/gates/gate_config.json`의 `"bootstrapped": true`, N3.12.6 ④(c))가 반영되면 이 행이 없는 것과 같다) / `그 커밋의 staged_diff 승인`(`Role: user` 커밋에 한해, 그 커밋이 **새로 더하는** 승인 기록 파일 하나이고 그 머리가 `target_kind: staged_diff`이며 `00-common` §8.2의 해시가 그 커밋의 나머지 변경과 맞는다 -- 기존 승인 기록의 수정·삭제와 두 번째 파일은 이 행에 맞지 않는다. **이 행의 `<id>`는 변경 id가 아니라 승인 기록 자신의 id다**(파일 이름이 `00-common` §8.1 id 형식이고 머리 `id`와 같다 -- `Role: user` 커밋에는 변경 id가 없다, 부트스트랩 재생 2차 검증 agent 지적) / `승인 기록`(사용자 확인과 승인 기록, U-16) / `status 전이만`(바뀐 필드가 status 전이 기록뿐이다) / `판정 트리`(주체 `사용자` 행에만 쓴다: 이 행의 glob 안에서 **다른 조건의 행 어디에도 맞지 않는 경로는 사용자만 쓴다** -- 판정 트리 안에는 '역할 밖'이 없다. Python이 import하거나 pytest가 읽는 새 파일(같은 이름의 패키지·모듈)이 트레일러 없는 커밋으로 판정 실행을 바꾸는 것을 이름 목록이 아니라 기본 거부로 막는다. 판정 트리에 새 종류의 파일을 두려면 먼저 이 표를 개정한다) / `판정 환경`(주체 `사용자` 행에만 쓴다: 이 행에 맞는 경로는 **다른 주체의 행에 맞아도 사용자만 쓴다** -- pytest가 rootdir부터 test 디렉터리까지 찾아 읽는 파일이라 어느 디렉터리에 있어도 판정을 바꾼다).

#### N3.12.3 변경 한 건의 흐름

**spec card** `docs/02-design/specs/<id>.spec.md`, `<id>` = `YYYYMMDD-<slug>`. 필드: Phase(N6.1의 Phase 이름. 판정 기록의 V `N/A`와 XFAIL 만료 판정 입력, `00-common` §9.3) / 의도 / 관찰 가능한 계약 / interface card / 판정 유형(`red-green`, `equivalence`, `test-only` 중 하나) / oracle 종류와 출처 / 거부해야 할 입력 / library 회로 적용 여부(DEC-47 대상 구분) / 무동작 판정 입력(볼 발동 계수 ID 목록과, 병합본이 더하는 새 산출물 필드마다의 무발동 값 -- `00-common` §11) / 활성화 IC 케이스(`<IC>:<case>` 목록, 이 변경이 PASS로 만드는 계약 test 케이스 -- `00-common` §9.3) / 재현할 수치 / 결정 필요 항목 / 승인 기록 링크.

**spec card 한 건의 단위** = **red 하나로 판정되는 관찰 가능한 계약 하나**다. 한 건이 소스 파일 여러 개를 건드려도 되지만, 판정 유형이 섞이거나(red-green + equivalence) 승인 기록이 둘 이상 필요하면 나눈다. 이동 전용 변경(Phase 3)은 모듈 하나가 한 건이고(N3.10 이동 규칙), test 전용 변경은 TS 단계 하나가 한 건이다(N3.11). design 문서가 내는 spec card 목록(N9.2-5)은 이 단위로 만든다.

| 2 | test-author | test 작성, 커밋(`Role: test`) |
| 3 | auditor | 오케스트레이터가 `git worktree add ../wt/<id>-audit -b role/audit/<id> role/test/<id>`로 audit worktree를 만든 뒤, freeze: test 커밋 해시 기록. red-green이면 base에서 assertion 실패 확인(ImportError만의 실패는 신규 함수일 때만 인정), equivalence면 base에서 통과 확인 |
| 4 | 오케스트레이터 | `git worktree add ../wt/<id>-code -b role/code/<id> <test 커밋>` |
| 5 | code-author | 구현, 커밋(`Role: code`). test가 틀렸다고 보면 고치지 않고 `docs/02-design/disputes/<id>.md`에 근거를 써서 커밋하고 멈춘다 -> 오케스트레이터가 worktree 정리 전에 spec card에 dispute 기록(원문 인용)을 남기고 사용자 결정을 받아 1로(`05-role-separation` §12 재시도) |
| 6 | 오케스트레이터 -> auditor | 오케스트레이터가 audit worktree에서 code 브랜치를 `--no-ff`로 병합한다(트레일러 `Role: doc`·`Change-Id`, 병합 커밋 트리 = code 끝 트리). auditor가 그곳에서 병합본을 검증(N4.2)하고 판정 기록을 커밋한다 |
| 7 | 오케스트레이터 | audit 브랜치 끝(판정 기록 커밋)을 gate 저장소 `master`로 push한다(`pre-receive`의 EL4가 통과시킬 때만 반영된다). 로컬 master는 그 뒤 gate에서 fast-forward로 받는다. EL4는 병합 아닌 커밋마다 트레일러·경로를 검사하고, 병합 커밋은 변경 한 건 구조의 병합(첫 부모 = test 끝, 둘째 부모 = code 끝, 트리 = code 끝 트리, `Role: doc`)이거나 **역할 밖 병합**(부모 둘, 첫 부모가 base와 같거나 그 후손, 역할 경로에서 트리가 첫 부모와 같다 -- 다른 skill·RTL 작업, `05-role-separation` §8.2-3 (라))일 때만 받는다 |

* 판정 유형: 동작을 바꾸는 변경은 `red-green`(새·바뀐 test가 base에서 FAIL, 병합본에서 PASS). 동작을 보존하는 변경(TS1, Phase 2 통합, Phase 3 이동)은 `equivalence`(test 커밋이 그대로이고 base와 병합본 모두 통과, 추가로 TS1은 stdout 동일, Phase 3은 AST 해시 동일).
* test 전용 변경(판정 유형 `test-only`: TS0·TS2·TS3·TS5·TS7, TS6의 probe 승격·삭제, Phase 3 T0·T1(계약 test의 정의 위치 독립화·test 파일 재배치 -- Phase 3 design 30 §8), redteam 데이터만 바꾸는 게이트 변경): 순서 4·5를 생략한다. 증거 = 변경 전 test 집합이 base에서 통과시킨 섹션을 변경 후 test가 모두 PASS함(섹션->test 매핑표는 `10-test-separation` design).
* oracle은 4종만(N0.4). 피검 함수 호출이나 피검 식 복사, 현재 출력 붙여넣기로 기대값을 만들지 않는다. **선택 기준**: 물리 불변식(KVL·KCL·VGS 정합·단조성)이나 구성으로 정답이 정해진 합성 입력으로 표현되면 (a), 다른 방법의 폐형식·축소 격자 전수탐색이 가능하면 (b), 기준선이 존재하고 동작 보존 변경이면 (c), 회로 해석 결론이나 사용자가 선언한 스펙값이면 (d)다. 두 종 이상 가능하면 **(a)를 우선**하고(피검 구현과 가장 멀다), 고른 종과 그 근거를 spec card의 'oracle 종류와 출처'에 적는다.
* 판정은 PASS / FAIL / XFAIL 세 값. XFAIL은 reason에 담당 Phase와 만료(그 Phase DoD)를 적고, 만료되면 FAIL. "참고" 출력과 소비자 없는 경고 리스트는 금지.
* 기준 약화는 test-author 커밋이라도 승인 기록이 있어야 병합된다(N6.3 `criteria_weakened` -- 옛 인용 'DEC-40, V5'는 폐기된 gate 규칙이라 정정; design이 지운 대상의 test는 `retired_tests`, O-155 B1).

#### N3.12.5 기록 양식

* **판정 기록** `.ai/verification/<id>.json`: `id`, `spec_card`, `evidence_type`(red-green / equivalence / test-only), `base_commit`, `test_commit`, `red{test_ids, failure_hashes}` 또는 `equivalence{commands, outputs_hash}`, `code_commit`, `checks{V1..V10: PASS|FAIL|N/A + 근거}`, `reproduced_numbers[{name, value, command}]`, `approvals[]`, `auditor_run{time, worktree, commands}`. **이 절은 필드 목록의 정본**이고, 필드마다의 타입·필수 여부·열거값(`evidence_type` ∈ {red-green, equivalence, test-only}, `checks` 값 ∈ {PASS, FAIL, N/A}, 해시 문자열 형식, 배열 원소 스키마)을 확정한 JSON Schema `.ai/verification/_schema.json`은 `00-common` design이 쓴다(산출물 목록 N3.12.6). 로더는 스키마 밖 필드를 거부한다.
* **승인 기록** `.ai/approvals/<id>.md`: 사용자 원문 인용, 날짜, 대상(diff 해시, 결정 ID, 또는 계획서 판정 표 파싱 값의 해시 -- `00-common` §8.2), 범위. 오케스트레이터만 쓴다. V5는 diff 해시 일치로 판정한다.
* **dispute** `docs/02-design/disputes/<id>.md`: 문제의 test, 근거(oracle 또는 사용자 원문), 요청.
* **interface card**: 기존 함수는 AST 시그니처 + docstring 첫 단락, 신규 함수는 spec card의 시그니처 절.
* **보고 수치**: spec card "재현할 수치" 절의 항목만 auditor가 명령과 함께 재실행해 판정 기록에 적는다. 최종 보고는 판정 기록의 값만 인용한다.

#### N3.12.6 부트스트랩과 산출물

부트스트랩 역할(2026-09-21 사용자 결정): 게이트 코드는 **작성 agent**가 쓰고, 공격 재생 데이터는 **검증 agent**가 설계 문서만 보고 코드보다 먼저 쓴 뒤 작성본에 재생하며, 오케스트레이터는 결과를 위협 범위(N3.12.0)로 분류해 범위 안 결함을 작성 agent에게 돌려보내는 감사만 한다(코드를 직접 고치지 않는다, WP-13·WP-22). 부트스트랩 순서(Phase 0.5): ① **작성 agent**(오케스트레이터가 맡긴다)가 agent 정의 3개, hook·게이트 스크립트(merge gate의 판정 기록 로더·계획서 판정 표 읽기·승인 기록 머리 파서 포함, `00-common` §8·§9), 양식 초안을 작성하고 `.gitignore`에 `library/*.search_archive/`, `runs/`를 등록(이 단계에 한한 예외, 사용자 승인) ② 더미 hook이 stdin을 파일에 기록하게 해 세 역할과 메인 세션에서 hook 입력 필드를 실측 ③ 공격 시나리오·과거 사례 재생(N4.3)을 실행해 로그를 사용자에게 제시하고 승인 기록 ④ 순서대로 -- (a) `.githooks/*` 갱신(사용자 경로, 승인 기록과 함께 한 번) (b) **사용자가** gate 저장소(로컬 bare, 위치·절차는 `05-role-separation` §13.1)를 만들고 샘플 hook을 지운 뒤, 작업 저장소에 원격 `gate`(절대 경로)를 등록하고 현재 master를 push해 기준 커밋(`baseline_commit`)으로 삼고, 감사 로그 첫 줄을 쓰고, `pre-receive`(`tools/gates/gate/`의 원본)를 설치 (c) `baseline_commit`과 부트스트랩 완료 표지를 적은 `tools/gates/gate_config.json` 커밋을 gate로 push(이제 `pre-receive`가 판정한다) (d) `python install.py --only agents --project .`, `python install.py --only hooks --project .`로 설치(DEC-41)하고 등록 내용을 대조 ⑤ 설치 상태에서 공격 재생과 변경 한 건 전 과정(오거부 0). 이후 게이트 변경을 포함한 모든 변경은 N3.12.3 흐름으로(게이트 변경이 반영되면 사용자가 gate 사본과 hook을 다시 설치한다 -- `05-role-separation` §13.4).
