### D. 계획·결정 절차
17. **bkit PDCA.** 계획 → 독립 검증 → 승인 → design → 검증 + design↔계획 gap → 승인 → card → test → code → 감사 → gap. 계획과 다르면 계획부터 고친다.
18. **작성자 ≠ 검증자.** 기준 약화는 사용자 승인.
19. **새 근본원칙은 사용자 승인 뒤 적용**, 그리고 기존 규칙 전수 감사. **원칙 추가·개정이나 결정 추가·번복이 있으면** 그 원칙·결정을 읽는 기존 계획 문언·design·card(쓰인 것과 진행 중인 것 모두)를 전수 대조해 낡은 것을 찾는다. 감사자 ≠ 작성자. 낡은 card는 상태 표지를 달고, 계획 → design → card 순서로 개정한다(착수 전 card는 착수 조건, 진행 중 card는 즉시 정지·보고).
20. **사용자 결정도 재검토 대상 (O-208).** 결정은 합리적 설계를 위한 수단이므로 이미 내린 결정도 언제든 재검토한다. '승인됐다'·'승인 선례'는 근거가 아니다(사실 기록으로만). 결정을 추가·번복할 때마다 새 결정과 기존 결정(O-번호·DEC·U) 사이의 모순을 전수 점검한다(점검자 ≠ 권고 작성자). 모순이나 불합리가 있으면 따져서 재검토안(유지·수정·철회)을 대안 비교와 함께 다시 묻는다.
21. **권고는 물리·회로이론 검증과 함께 (O-171).** 물리 결정자 / 식·원문(쪽 + 로컬 PDF) / LUT·SPICE 실측 / 판정(맞음·조건부·틀림·불확실). 틀림·불확실이면 권고 전에 잰다.
22. **권고 전 확인.** 원칙 전수 자기 점검, 대안 비교표 + ⚠, 실현 가능성 실측, 회로 파일·선례 직접 읽기, 조건부 전제 n/N 실측, 계획 전체 grep, 열린 결정 상호작용, design 영향 대조, 마지막 커밋까지 독립 검증. agent·검증자 권고를 그대로 옮기지 않는다(원칙으로 재판정). agent의 결함·누락·'없음' 지적도 그대로 옮기지 않는다 -- 원 파일과 계획 기본 규칙(DEC)·엔진 기본값을 직접 열어 확인한 뒤에만 결함·대기열·질문 선택지로 올린다(O-179 C 열, O-188 bulk 기본 레일).
23. **열린 권고는 그 사이 결정·실측으로 갱신.**
24. **원래 취지와 다른 것은 표지하고 따로 보고.**
25. **계획서는 규칙·정의·게이트·완료 조건만**, 경위·정정 이력·측정 서술은 history.
